## 一、背景与目标

### 1.1 为什么在本仓做这六类功能

新农屿后端（`nongyu-backend-plus`）是**独立于旧农屿 monorepo 的全新仓库**，不复用旧后端代码、表结构与部署链路。除已交付的 WebVPN 能力、身份域/平台底座、教务查询与缓存之外，旧客户端里还常年依赖另外六类「不涉及学校侧系统」的常见功能——它们全部落在现行 PRD 显式排除的那一句里（[prd-学生校外访问学校服务.md](prd-学生校外访问学校服务.md):51「旧 monorepo 的其它业务（鉴权、会话、内容、广场）、埋点服务、Web 管理端……」）。

也就是说：**这六类功能不是 WebVPN effort 的延伸，而是一个与它并行的 effort。** 两者共用同一套平台底座（会话、role、缓存、限流、审计），但业务语义彼此独立，各自需要自己的 PRD 与 Spec。

### 1.2 六个功能各自要解决的问题

| 功能 | 现实问题 |
| --- | --- |
| **公告** | 学校/管理侧的通知现在只能由旧仓以「帖子的一个类型值」承载，读者范围、有效期、撤回都没有正式模型 |
| **帖子** | 学生的反馈与留言需要可回复、可点赞、可带图片的内容载体，且历史契约要求**对读者匿名** |
| **站内消息（通知/内部信）** | 旧仓根本没有消息中心：所谓「通知」只是前台轮询 + 一个行级布尔位，收件人恒为帖主，无法表达多收件人与已读 |
| **用户行为埋点** | 客户端行为数据目前依赖一个已下线的旧 Go 埋点服务，本仓没有落点 |
| **文件存储（MinIO）** | 帖子附件需要一个对象存储落点，且业务域不得直接依赖 S3 SDK |
| **B 端管理（管理台后端 API）** | 管理动作需要统一的后端 API，鉴权与审计口径必须与既有身份域一致，而不是再长一套 RBAC |

### 1.3 目标

1. 六类功能在**不新增独立服务、不新增数据库、不重开 MinIO 选型**的前提下，有正式的 PRD 与可判定的验收口径。
2. 六域之间的横切依赖（附件、通知触发、鉴权与审计）各自**只在一处定义、其余引用**，避免两套实现。
3. 明确「对齐旧农屿契约」在本 effort 的含义：**产品语义对齐，不承诺 HTTP 路径与信封逐字一致**（[#44 决议](<../tech/决策-公告域模型与作用域.md>):24 的全域口径）。

## 二、范围

### 2.1 包含

1. **B 端管理（管理台后端 API）**：管理台所需的后端能力集合，复用既有 `role` 三档（0/1/2）与 `scope=admin` 会话。管理端 UI 在 `nongyu-web-admin`，**不在本仓**。
2. **用户行为埋点**：客户端行为事件的采集与上报，以及一个最小的计数读取口。
3. **文件存储（MinIO）**：对象存储的接入落点，供帖子附件使用；对象 key 规范与上传方式的细节**待 [#53](https://github.com/NongyuSystem/nongyu-backend-plus/issues/53) 收敛**（选型不再重开）。
4. **帖子**：用户内容实体（含回复/留言、点赞、收藏、24h 内本人编辑、附件）。
5. **公告**：管理台发布、面向指定范围用户、客户端只读的内容实体（含状态机、时效与置顶）。
6. **站内消息**：通知与内部信两类形态的统一 per-user 投递与已读。

### 2.2 不包含（13 条，逐条摘录自 #47 决议 Q4）

**原已列明的 7 条**

1. **管理端 UI**：管理台前端在 `nongyu-web-admin`，本仓只做后端 API。
2. **完整 RBAC**：只做既有 `role` 三档 + admin 会话 + fail-closed，不建权限体系。
3. **运行日志 / 审计 / Elasticsearch 重定**：三层中「运行日志」与「审计流水」沿用既有结论，本 effort 只新增「用户行为埋点」这一层。
4. **MinIO 选型重开**：选型不再讨论；本 effort 只定接入落点（对象 key 与上传方式见 [#53](https://github.com/NongyuSystem/nongyu-backend-plus/issues/53)）。
5. **埋点查询分析平台**：不做看板、不做明细查询与导出，只留最小计数口。
6. **旧代码 / 表结构 / 部署链路复用**：一律不沿用。
7. **可运行代码与 PR**：本 PRD 及后续 Spec 阶段都不产出实现代码。

**本图新增的 2 条**

8. **旧仓 Admin JWT「永不过期」口径**：已推翻；管理台会话必须可吊销、有明确过期、fail-closed。
9. **把 `notified_author` 行级投递位照搬成 per-user 已读**：不照搬；per-user 已读由站内消息域承接。

**由已关子票导出的 4 条**

10. **把埋点做成独立服务**（[#45](<../tech/决策-用户行为埋点.md>) Q1）：不做独立服务、独立端口、独立库；埋点是本仓内的一个业务域。
11. **照抄旧 Track 的 `{ok,data}` 信封与队列满 503**（[#45](<../tech/决策-用户行为埋点.md>) Q2/Q5）：沿用本仓 `{code:string, message}`；缓冲满不返回 503。
12. **埋点域做 `presence/offline`（在线态回写）**（[#45](<../tech/决策-用户行为埋点.md>) D2）：不在埋点域做；如有在线态需求另立决策。
13. **要求 `/admin/*` 签 NY1、把业务公开读端点塞进 `publicPaths`**（[#46](<../tech/决策-横切鉴权口径.md>) Q1/Q4）：管理端不签 NY1；公开只读端点走独立的 `publicReadablePaths`，不混入 `publicPaths`。

## 三、用户故事

### 3.1 公告

1. 作为学生，我想在首页看到最新一条仍在有效期内的公告，这样我不会错过临时停课、考试调整这类有时效的通知。
2. 作为学生，我想看到**只针对我所在学院/年级/角色**的公告，这样我不用在全校通知里翻找我关心的部分。
3. 作为学生，我想按发布时间浏览公告列表并看到置顶公告在最前，这样重要的长期公告不会被我划过去。
4. 作为管理员，我想把公告先存成草稿再发布，或发布后撤回，这样写错内容的公告不会一直挂在学生面前。
5. 作为管理员，我想给公告设定生效与失效时间，这样过期公告自动从列表消失而不需要我手动清理。

### 3.2 帖子

1. 作为学生，我想在反馈板块发布一条带图片的帖子，这样我能把问题现场拍下来。
2. 作为学生，我想在帖子下留言，也想看到管理员给我的正式回复，这样我知道问题被谁处理到哪一步。
3. 作为学生，我想给帖子或留言点赞、收藏，这样我能标记有用的内容。
4. 作为学生，我想在发布后 24 小时内改正我的错别字或补充内容，超过之后就不能再改，这样我不会被误以为可以事后篡改。
5. 作为其他学生，我希望列表与详情里看不到别的作者是谁，这样我敢说真话；作为管理员，我在需要处理问题时能看到实名，且这次查看会被记录。

### 3.3 站内消息（通知 / 内部信）

1. 作为帖主，我想在帖子被回复或被点赞时收到一条站内消息，这样我不必反复刷新页面找反馈。
2. 作为留言作者，我想在留言被点赞或被回复时收到消息，这样我知道有人回应了我。
3. 作为学生，我想看到自己的未读消息数，并支持单条已读、全部已读，这样我不至于把消息漏掉。
4. 作为学生，我想给另一名已知用户发一条内部信，这样我能就具体问题私下一对一沟通。
5. 作为学生，我不想收到自己给自己的消息，也不想看到不相干的人被抄进我的消息里，这样消息里只有与我相关的内容。

### 3.4 用户行为埋点

1. 作为客户端，我想把一批用户行为事件一次性上报并在失败时只重传失败的那部分，这样弱网下也不会因为一条坏数据重发整批。
2. 作为客户端，我想在同一个事件重复上报时不被当成新事件计数，这样网络重试不会污染数据。
3. 作为产品维护者，我想按事件类型与时间窗看到计数汇总，这样我能判断某个功能有没有人用，而不必看任何个人明细。
4. 作为用户，我不希望我的密码、证件号、票据之类的信息被当作埋点上报或落库，这样即使我点了什么也不泄露敏感数据。
5. 作为运维，我希望埋点写不进去时业务请求照常成功，这样埋点故障不会让学生用不了别的功能。

### 3.5 B 端管理（管理台后端 API）

1. 作为管理员，我想在管理台登录后就能发布公告、处理帖子，这样我不需要再单独要一套账号。
2. 作为管理员，我想在管理台看到被匿名保护的作者真实身份，但只在处理具体问题时，这样匿名不成为追责的障碍。
3. 作为超级管理员，我想让「改角色」「打开/关闭某个集成开关」这类敏感动作只有我能做，这样普通管理员误操作不会扩大权限面。
4. 作为管理员，我想我做的每一个管理动作（删除、撤回、改角色、查看敏感字段）都会被记一条流水，这样事后能追溯是谁做的。
5. 作为安全负责人，我希望管理台会话会过期、也能被吊销，这样一台没退出的电脑不会长期敞着。

### 3.6 文件存储（帖子附件）

1. 作为学生，我想一次给一条帖子最多带 9 张图，单张不超过 5MB，格式限 jpg/png/webp/gif，这样我不必先自己压缩或转格式。
2. 作为学生，我想我的图片能稳定地显示出来，而不是过一段时间就变成坏链接，这样我的帖子不会烂掉。
3. 作为客户端开发者，我不想为图片存储单独接一套认证或密钥，这样客户端不因为存储而多一份凭据。
4. 作为后端维护者，我希望业务代码只说「存这个附件、取这个附件」，不直接依赖某个 S3 实现，这样将来换存储不牵动业务。

## 四、验收标准（从用户视角，可判定）

> 本节只写「能看见什么算成」，不写实现。括号里是该条承接的上游决议；**域模型的细节一律以决策笔记为准，本文不重述**。

### 4.1 公告

1. 未登录用户可以打开公告列表、公告详情、以及首页「最新一条公告」。列表与 `latest` 只包含**已发布且仍在有效期内**的公告；**草稿与已撤回**的公告对任何非管理端调用方在列表、`latest`、详情三处都不可见。（[#44](<../tech/决策-公告域模型与作用域.md>) Q2/Q3、[#46](<../tech/决策-横切鉴权口径.md>) Q1）
2. 一条按角色/学院/年级定向的公告，只对该范围内的用户出现在列表中（含 `latest`）；范围外的用户在列表里看不到它。「定向公告的详情是否对范围外用户开放」**待 Spec 收敛**——#44 Q1 只定了「读列表时按当前用户 `StudentBrief` 过滤」，未定详情口径。（#44 Q1）
3. 一条已过 `expiresAt` 的公告不再出现在默认列表与 `latest` 中，但仍可按 id 打开详情；置顶公告在列表中排在非置顶之前，同级按发布时间倒序。（#44 Q2）
4. 首页 `latest` 在「没有任何已发布且有效」时返回空值而不是报错；有多条符合条件时只返回置顶优先、发布时间最新的一条。（#44 Q3）
5. 公告被撤回后，用户侧不再能通过任何列表或 `latest` 看到它。（#44 Q2）

### 4.2 帖子

1. 任何非管理端调用方在帖子列表与详情中**拿不到作者的身份标识**；同一条帖子的回复/留言同样匿名。作者本人能识别「这条是我的」（`isMine` 类语义），但这不是把身份下发给第三方。（[#49](<../tech/决策-帖子域模型与契约.md>) Q2/Q12）
2. 一条帖子最多带 **9 张**附件，单张超过 **5MB** 或格式不在 `jpg|png|webp|gif` 内时被拒绝，且拒绝信息能指出是超数量、超大小还是格式不对。（#49 Q4；该上限来源为广场发帖增强 PRD 的**提案**，由 #49 Q10 升格为本期硬约束）
3. 帖子列表按板块过滤、按发布时间倒序、可继续翻页到更早内容，不出现重复或漏项。（#49 Q5）
4. 发布满 24 小时后，作者再尝试编辑会被拒绝；窗口内的编辑能成功，且编辑后的内容会带上「已编辑」的时间信息。（#49 Q3）
5. 点赞与收藏可以重复取消/重新建立，同一用户对同一目标只会被算作一次；对留言的点赞/收藏与对帖子的一样可用。（#49 Q7/Q12）
6. 回复/留言只有两层语义（帖子 ↔ 留言），不存在「回复的回复」的嵌套层级；管理员回复与学生留言在用户侧可区分。（#49 Q3/Q11）

### 4.3 站内消息（通知 / 内部信）

1. **已读是 per-user 的**：同一台设备读完，另一台设备上同一条也是已读；一个用户读过不会影响另一个用户的未读状态。（[#55](<../tech/决策-消息域模型.md>) Q1/Q4）
2. 未读数是「我的、未读的、未删除的」条数；删除一条未读消息后未读数随之减少；「全部已读」作用于当前筛选条件下的全部消息。（#55 Q4）
3. 帖主收到「帖子被回复」「帖子被点赞」的通知，留言作者收到「留言被点赞」「留言被回复」的通知；同一条来源在短时间内被多次触发时，用户看到的是**一条被合并的消息**而不是刷屏。（#49 Q11、#55 Q3）
4. 公告发布后，落在其受众范围内的用户会收到一条通知；把同一条公告编辑重发不会让用户重复收到。（#44 Q4、#55 Q3）
5. 内部信只能发给**已存在**的用户、**不能发给自己**，正文有长度上限，发送频率有上限；发送者实名可见（与帖子匿名的取向刻意相反）。（#55 Q2）
6. 用户不能通过任何公开接口「凭空创建一条通知」——通知只能由系统或他人动作派生；能主动创建的只有内部信。（#55 Q5）
7. 消息列表只展示本人消息；分页可取更早消息，可按类型与「仅未读」筛选。（#55 Q5）

### 4.4 用户行为埋点

1. 一批事件可以一次上报（1~100 条），其中部分条目不合格时**其余条目仍然被接收**，返回里能分别看出「已接收 / 重复 / 被拒」的数量。（[#45](<../tech/决策-用户行为埋点.md>) Q5）
2. 同一个事件重复上报不会产生两条记录，也不被算作失败。（#45 Q5）
3. 超过请求体积上限的上报被明确拒绝，而不是被静默截断后当成成功。（#45 Q5）
4. 上报内容里出现密码、证件号、票据、令牌类字段时，这些字段不会落库；未知字段被丢弃而不报错；业务属性超长会被截断到上限内。（#45 Q6）
5. 记录里的用户身份来自服务端已认证身份，客户端自报的身份不能覆盖它。（#45 Q4）
6. 埋点写入受阻（缓冲满、下游慢）时，业务请求**仍然成功返回**，不会因为埋点而出现 5xx 或要求客户端重试。（#45 Q3/Q5）
7. 计数汇总口只提供「按事件类型 + 时间窗的计数」，不提供任何个人明细、不提供导出。（#45 Q6）

### 4.5 B 端管理（管理台后端 API）

1. 所有管理端点都要求**管理台会话**：普通 App 会话、过期会话、被吊销的会话一律进不去；角色低于门槛的账号同样被拒，且拒绝是默认行为而不是靠某个开关打开。（[#46](<../tech/决策-横切鉴权口径.md>) Q2）
2. 改角色、开关某个集成开关、读取敏感字段这三类动作要求**更高一档角色**；其余管理动作按普通管理员门槛。（#46 Q2/Q6）
3. 管理员查看被匿名保护的作者身份时，系统同时留下一条可追溯记录；管理动作（删除、撤回、改角色、开关切换、读取敏感字段）各自一条记录，记录里只有标识性字段，不含票据、密码、验证码、上游响应体。（#46 Q3/Q6）
4. 管理台会话有明确过期时间、可主动吊销；不做「永不过期」。（#46 D1、第 2.2 节第 8 条）
5. 管理端**不需要**请求签名（浏览器拿不到 App 密钥）；App 侧业务端点仍按既有分层要求签名。两侧口径不混用。（#46 Q4）

### 4.6 公开读端点范围

1. **免登录可读的只有 5 个只读端点**：公告列表、公告详情、最新公告、帖子列表、帖子详情；除此之外（回复/点赞/收藏、消息、埋点上报、以及全部管理端点）一律要求登录。（#46 Q1）
2. 免登录端点与「取得身份类」公开路径**不是同一份清单**，前者不污染后者的原语义；但判定仍只有一处入口。（#46 Q1）
3. 公开读端点仍受限流约束，且不因为「公开」而获得额外豁免。（#46 D2）

### 4.7 文件存储

1. 用户在帖子中上传的图片在后续访问时仍可正常取到，链接可直接用于展示，无需用户额外登录存储服务。（#49 Q4、#53）
2. 图片存储不向 App 客户端分发额外的长期凭据，存储侧不承担用户身份认证。依据是调研笔记里的转述「MinIO 不提供身份认证」，**该行为未经实测**，具体口径待 [#53](https://github.com/NongyuSystem/nongyu-backend-plus/issues/53) 收敛。（[调研底稿](<../tech/调研-六类常见功能的旧农屿一手契约与新仓现状.md>):65-66）
3. 业务代码通过统一接缝访问对象存储，不直接依赖具体 S3 实现；换存储实现不要求改业务域。（`README.md`:44-48「架构约束」第 1/2 条）

### 4.8 横切（六域共用）

1. 六域的写操作失败时不会互相拖垮：通知写入失败不导致帖子/公告发布失败，埋点写入失败不影响任何业务端点。（[#47](<../tech/决策-六功能范围切分.md>) Q5、[#45](<../tech/决策-用户行为埋点.md>) Q3）
2. `audit_log.action` 的命名符合 `<域>.<动作>` 形式，示例集（`post.delete`、`announcement.publish`、`user.role_change` 等）可被 Spec 直接扩展为完整取值表。（[#46](<../tech/决策-横切鉴权口径.md>) Q3/D4）
3. 请求链路顺序对所有新端点一致：请求标识 → 签名（适用时）→ 会话鉴权 → 管理端门槛（仅管理端点）→ 限流。（#46 Q5）
