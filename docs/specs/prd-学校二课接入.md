## 一、背景与目标

### 1.1 为什么在本仓做学校二课

学校二课（PU / 口袋校园，川农定制版「i川农」）是学生查询第二课堂学分、浏览并报名活动、现场扫码签到的**第三方平台**。它与「教务」是两个不同系统、两套独立凭据。

现行 PRD（[prd-学生校外访问学校服务.md](prd-学生校外访问学校服务.md)）把「旧 monorepo 的其它业务」列为**不包含**；本 PRD 不改那句话，而是**另立一个与 WebVPN／身份域／教务查询并行的 effort**，共用同一套平台底座（会话、缓存、限流、审计），业务语义独立。

### 1.2 要解决的问题

| 问题 | 现实表现 |
| --- | --- |
| 学生手机上要装第二个 App | 二课功能在 i川农（PU 客户端），与农屿并列；学生被迫在两个 App 间切换 |
| 农屿看不到二课学分 | 第二课堂学分是毕业硬要求，但农屿只展示教务成绩，学生无法一站式查看 |
| 报名与签到链路不透明 | 学生在农屿内无法得知「这个活动怎么报名、现场怎么签到」 |
| 后端拿不到二课数据 | 无任何二课数据落点，将来想做活动聚合也无从下手 |

### 1.3 目标

1. 二课的**读写能力在农屿可用**——客户端持本人凭据直连，后端下发「怎么请求」。
2. 后端**不持有任何二课凭据、不向二课发起任何请求**（安全边界见 §2.3）。
3. 后端为二课预留**记录能力**：审计流水必有，数据副本尽力而为。
4. 明确「对齐 PU 契约」在本 effort 的含义：**产品语义对齐 APK 逆向出的契约，不承诺路径与信封逐字一致**（沿用 #44 全域口径）。

## 二、范围

### 2.1 包含（A + B 两组，共 61 接口）

1. **A 二课学分 / 成绩单（13 接口）**：学期学分、申请类学分、导入明细、诚信值、学分规则说明、成绩记录明细（含按类型）、综测明细、排名、成绩单（查看/设置/保存设置/预览）。
   → 回答「**我的二课成绩长什么样**」：总分 → 分项 → 明细 → 规则 → 排名 → 可导出成绩单。

2. **B 活动（48 接口）**：活动列表/详情/成员/状态/类型层级/标签/部落分组/搜索/花絮（读类约 35）；报名、签到签退、评价、发布与编辑活动、收藏、附件登记（写类约 13）。
   → 回答「**能参加什么、怎么参加**」。

**A 回答「我得了多少」，B 回答「我能参加什么」——同一产品语义的两面，拆开都不成立。**

### 2.2 不包含（逐条摘录自 [#59 决议](<../tech/决策-二课范围切分与OutOfScope.md>)）

**C 组 · 部落/社群（37 接口）**：整体不纳入。理由：PU 的社群产品线，非「第二课堂成绩」语义；其相册与本仓 `content/post` + `platform/objectstore` 功能重叠。

**D 组 · 用户/账号/设置（55 接口）**：拆三类，**0 个进入本 effort 业务域**——
- 12 个登录/凭据方法：**客户端自理**（见 §2.3），后端不参与；
- 8 个画像扩展：**复用身份域**，不为二课建画像域；
- 其余 47 个（隐私设置 / 第三方绑定 / 手机绑定改密 / 社交图谱 / 首页运营位 / 反馈 / 基础字典）：**不做**。

**E 组 · 消息/通知/私信（19 接口）**：整体不纳入。本仓已在 #43 用 `internal/message` + `internal/content/announcement` 建过同类能力，不重复造域。
→ **硬边界**：活动变更通知应发**本仓消息域**，**不对接** PU 的 `messageSystemNotice`。

**其它明确不做**：
- 不做 H5 页面接口对接（10 条 `?token=` 页面，真实接口不在 APK 产物内）；
- 不做成绩单 PDF 生成与存储（URL 指向 PU 侧资源）；
- 不做活动附件 multipart 中转（客户端直传 PU）；
- 不做二课数据的服务端**代取**缓存（零出站；客户端**回传**的副本不属此条）；
- 不为 C/D/E 建任何端点、缓存或数据表。

### 2.3 凭据与直连边界（本 effort 最不可动摇的一条）

**客户端持本人 `x-access-token` 发起全部读写请求；后端零出站、零凭据。**

- 后端**不持有、不代管、不下发、不落库** PU 凭据；
- **不使用密码镜像代用户登录 PU**——这会把「库泄即学校账号泄露」的风险外溢到一个本仓无法审计的第三方；
- 客户端直连段的失败由**客户端**判定（含 `code=5` token 失效）。

依据：[ADR-0001](<../adr/0001-服务端代请求边界由新后端重写.md>) 二课追加节 + [#69 决议](<../tech/决策-二课凭据边界与ADR-0001再修订.md>)。

## 三、用户故事

### 3.1 二课学分与成绩单（读类）

1. 作为学生，我想在农屿看到本学期已获得的第二课堂学分，这样我不用打开第二个 App 就知道毕业要求还差多少。
2. 作为学生，我想按学期查看学分明细（哪些活动给了多少分），这样我能核对某次活动到底有没有被计入。
3. 作为学生，我想看到诚信值以及它是怎么被扣的，这样我知道报名后爽约的代价、避免影响后续报名。
4. 作为学生，我想看到学分规则说明，这样我理解「什么算、怎么算」，而不是只看到一个不解释的数字。
5. 作为学生，我想看综测明细与排名，这样我知道自己在班级/专业中的位置。
6. 作为学生，我想生成并调整个人的成绩单（决定展示哪些项），这样我能在评优评先时直接出示。

### 3.2 活动浏览与报名（B 组读类 + 写类）

7. 作为学生，我想按类型/等级/部落/关键词筛选活动列表，这样我能快速找到自己能参加且感兴趣的活动。
8. 作为学生，我想看活动详情（时间、地点、名额、主办方、报名条件），这样我判断是否值得报名。
9. 作为学生，我想看到活动已报名成员，这样我了解参与人群。
10. 作为学生，我想在 App 内完成报名，这样我不用切到 PU 客户端。
11. 作为学生，我想到现场扫码签到，这样我的到场被如实记录、诚信值不受影响。
12. 作为学生，我想在现场签退，这样完整参与的活动能拿到全部学分。
13. 作为学生，我想在活动结束后评价，这样我的反馈能影响后续活动质量。
14. 作为学生，我想上传活动花絮，这样活动留下可回溯的记录。
15. 作为组织者，我想在农屿内发布/编辑活动，这样我不必切回 PU 客户端准备活动。

### 3.3 凭据与登录

16. 作为学生，我想明确知道「农屿不需要我的二课密码」，这样我敢用这个功能。
17. 作为学生，我想在二课凭据失效时被明确提示并引导重新登录 PU，而不是看到一个含糊的「请求失败」。
18. 作为学生，我想退出农屿登录后，任何二课相关凭据都不残留在服务端，这样我不用担心换设备后被人接着用。

### 3.4 记录与可观测

19. 作为维护者，我想知道「谁在什么时候问了哪个请求配方」，这样出现问题能追溯。
20. 作为维护者，我想在后端留有二课数据的只读副本（当客户端愿意回传时），这样将来做活动聚合有数据基础。
21. 作为维护者，我想清楚知道后端**没有**观测到客户端直连那一段，这样我不会误以为已有全量限流与审计。

### 3.5 失败与边界

22. 作为学生，我想在网关不可达/网络失败时看到「这是本地网络问题」而不是「服务器错误」，这样我知道该找谁。
23. 作为学生，我想在我重复扫码时得到明确结果（成功或已签到），而不是不确定状态。
24. 作为维护者，我想在文档里看到「二课 token 无 refresh/吊销、有效期未知」，这样我在做安全评估时不至于高估防护。

## 七、已知风险与开放项

### 7.1 未验证事实（证据等级铁律，**不得当作已确认**）

| 项 | 现状 | 影响 |
| --- | --- | --- |
| **二课 `data` 的响应形状** | 离线 APK 只有请求参数、**无响应体**；三套壳（`BaseResponse<T>`/`RespVO`/`BaseRespVO`）里每类数据落在哪套、`data` 是数组/对象/包装对象**均未知** | **schema 写不出来**——数据副本的形状校验无法定稿。这是 Spec 的**真阻塞项** |
| **`code=0/5` 的真实语义** | 来自转换器 IL 静态判读，**未在真实响应验证** | 客户端错误态判定可能与实际不符 |
| **PU token 真实获取/刷新/失效行为** | 产物里**无 refresh/renew/logout 端点**，token 有效期未知 | 无法承诺「泄露后可止损」；这也是否决「后端代持 token」的核心依据 |
| 签到二维码 `qrCodeTimestamp` 时效 | 未知 | 客户端重放窗口无法界定 |
| 二课限流/风控按账号还是 IP | 未知 | 「推给客户端节流即可规避」**不作承诺** |
| 重复扫码/重复报名的服务端行为 | 未知（报错？幂等成功？） | 幂等责任只能交客户端，不能写死契约 |
| `pu-version` 等 7 个设备头是否必需 | 只挂 `getGsonApi`、Rx 侧不带；真实要求未知 | 配方是否需要声明设备头待定 |
| 活动详情是否含「主办部落名」「学院名」 | 取决于真实响应字段 | 若含，则 #59 的 61 接口范围可能 +1~2 |

### 7.2 结构性风险（已接受或已规避）

| 风险 | 处置 |
| --- | --- |
| 后端对客户端直连段**零观测** | **已接受**（ADR-0001 第 4 条）。文档必须写明「后端观测不到」，**不得声称已限流已审计** |
| 数据副本**不可验证真伪**（客户端可伪造/不上报/只报一部分） | **已接受**，但**写死**：只能作「已知内容的只读副本」，**不能作权威来源**用于对外展示或统计 |
| 二课平台 `jk` **公网可达**（不像教务校外不可达） | 鉴权与限流按 #63 执行不放松；不因 jiaowu 先例降低标准 |
| 活动发布/编辑类配方是否给普通学生 | **未定**。按角色下发不同配方集需要角色判定口径，本图无票覆盖 → 转 Spec 或另开 effort |

## 八、交付边界

**本 effort 交付什么：**
- 一份 PRD（本文）+ 一份 Spec（由 #64 收口）
- 六份决策笔记 + ADR-0001 追加节 + GLOSSARY 第 ④ 段

**本 effort 不交付什么：**
- **可运行 Go 业务代码**、PR、数据库迁移、部署链路切换
- 二课凭据的任何形式托管
- 对二课平台的任何服务端请求
- C/D/E 三组的任何端点、缓存或数据表
