# 决策：二课写类请求配方的契约形状

> **性质**：wayfinder map [#58](https://github.com/NongyuSystem/nongyu-backend-plus/issues/58) 子票 [决议：写类请求链路下发的契约形状](https://github.com/NongyuSystem/nongyu-backend-plus/issues/62) 的决议产物。
> **不是实现方案、不产可运行代码**。
> **与 #61 的分工**：**#61 管「记录什么」，本票管「怎么发」**。本票只定**配方的形状**（一条配方含哪些字段、多跳怎么表达），不定记录语义。
> **拍板**：2026-11-16。

---

## 〇、本票实际范围已收窄（与题干不同）

题干说「写类请求链路」，并列出要覆盖 `updateActivity`（24 字段）、`saveReportCardSetting`（8 字段）等。但 [#59](https://github.com/NongyuSystem/nongyu-backend-plus/issues/59) 已把范围收敛，且 [#61](https://github.com/NongyuSystem/nongyu-backend-plus/issues/61) 已确认「读写两端形状对称」——

**所以本票定的不是「写类专属形状」，而是「二课请求配方的统一形状」**：读写共用一套字段，只有 `method`、参数槽位的内容不同。这样 #61 的读类配方与本题的写类配方是**同一个结构化契约**，Spec 里只需写一遍。

## 一、配方形状（核心）

### 1.1 一条配方 = 一个目标 + 一个动作

```jsonc
{
  "id": "secondclass.activity.signInOrOut",   // 稳定标识，客户端按它请求
  "target": "secondclass",                     // 逻辑目标名（后端映射为 host）
  "method": "POST",                            // GET | POST（二课写操作全是 POST）
  "path": "/act/actInfo/v1.0.0/signInOrOut",   // 二课端点路径（注解值本身即绝对路径）
  "contentType": "form",                       // form | none
  "auth": { "in": "header", "name": "x-access-token", "from": "client" },
  "params": [ /* 见 1.2 参数槽位 */ ],
  "fields": [ /* 见 1.4 多文件字段 */ ]
}
```

**逐字段说明**：

| 字段 | 取值 | 为什么需要 |
| --- | --- | --- |
| `id` | 稳定字符串，形如 `secondclass.<资源>.<动作>` | 客户端按 id 要配方，**不按 URL**——这样后端能改后端路径而不破坏客户端 |
| `target` | 逻辑目标名（`secondclass`） | **ADR-0001 第 1 条**：调用方永不传 host，只传逻辑名 |
| `method` | `GET` / `POST` | 读写共用一套，靠它区分 |
| `path` | 二课端点路径（绝对路径常量） | 二课注解本身是绝对路径（[#67 结论](https://github.com/NongyuSystem/nongyu-backend-plus/issues/67)）；后端拼成完整 URL 下发 |
| `contentType` | `form` / `none` | 172 个接口**全是** `FormUrlEncoded` 或 `Multipart`；`form` 表示 `application/x-www-form-urlencoded` |
| `auth` | `{in, name, from}` | 明确「凭据放哪、叫什么、谁提供」。`from: "client"` 表示由客户端持有（#69 结论）；**后端不填值** |
| `params` | 参数槽位数组 | 见 1.2 |
| `fields` | 文件字段数组 | 见 1.4；无文件时为空 |

**不要的字段（相对 jiaowu 的删减，理由必须记下）**：

| jiaowu 有 | 二课为什么不要 |
| --- | --- |
| `parser`（`jiaowu-course-v1`） | 二课是 JSON API，客户端拿到 `data` 直接用，**没有解析 HTML 这一步** |
| `session`（`ok`/`unavailable`） | jiaowu 有它因为「后端建会话可能失败但仍 200」；二课后端**不建会话**（#69），此态不存在 |
| `cookies[]` | 二课凭据是 header `x-access-token`，不是 cookie。用 `auth` 表达更准 |

### 1.2 参数槽位（本票最重要的新增结构）

jiaowu 的 recipe 没有这一层——它的 GET 参数已全部烘进 `address`。二课不行：`actId`、`memberId`、`qrCodeTimestamp`、GPS 坐标这些**必须客户端在发起时决定**。

```jsonc
{
  "name": "qrCodeTimestamp",
  "required": true,
  "origin": "client_local",     // client_local | fixed | optional
  "note": "扫码瞬间的毫秒时间戳，必须由客户端现场生成"
}
```

**`origin` 三值定义了「这个值从哪来」**：

| origin | 含义 | 例子 |
| --- | --- | --- |
| `client_local` | **必须客户端现场产生**，后端绝不代填、绝不伪造 | `qrCodeTimestamp`、`signupLong`/`signupLat`、`codeTime`、`gpsCode` |
| `fixed` | 由配方直接给出的常量，客户端照填 | 某些固定 `type`/`version` 参数 |
| `optional` | 可选，客户端可传可不传 | 分页 `page`、筛选 `status` |

**硬约束（从 #69 Q3 的第一性理由延续）**：`origin: client_local` 的参数，**后端既没有它的值，也不该有**——GPS 坐标、扫码时间戳、诚信值扣分是「本人当场发生」的事实，后端伪造即为造假。

### 1.3 多跳：默认单跳，需要时用 `steps`

jiaowu 是单跳。二课存在「先取再写」的场景（如某些签到要先拿 `memberId`）。

**决定：配方默认单跳；多跳时用有序 `steps`，每个 step 自己是一条配方。**

```jsonc
{
  "id": "secondclass.activity.signInWithLookup",
  "steps": [
    { "ref": "secondclass.activity.getActMemberList" },
    { "ref": "secondclass.activity.signInOrOut",
      "params_from": { "memberId": "$.steps[0].data.myMemberId" } }
  ]
}
```

**三条边界**：

1. **`steps` 只是「引用 + 取值路径」，不是「后端驱动的流程」**——后端不下发控制流，只声明「这两步有先后、第二个的某参数来自第一个的响应」。
2. **取值路径 `$.steps[n].data.xxx` 是客户端自己解析**，后端不代解（它拿不到响应）。
3. **能不写多跳就不写**：绝大多数写操作是单跳（下面 §二 的 13 个里只有签到系列可能需要）。**多跳是例外，不是默认。**

### 1.4 文件字段（multipart 场景）

B 组有 4 个 multipart 接口（`addTrivia`、`saveActivity`、`updateActivity`(multipart 版)、`saveGroupInfo`）。其中**纳入范围**的只有活动相关的那几个。

```jsonc
{
  "name": "file",
  "required": false,
  "kind": "file",              // file | text
  "note": "封面图；客户端直传二课，后端不中转"
}
```

**硬约束**：文件**由客户端直传二课**，后端**不碰字节流**（#59 Out of scope 已定：不做活动附件中转、与 MinIO 无关）。

## 三、后端不做什么（硬约束，逐条）

1. **不代发**：后端绝不向二课发起 `POST`（零出站，ADR-0001 二课追加节第 2 条）。
2. **不重试**：没有「后端替客户端重试」这回事——后端连第一次都不发。
3. **不回显上游响应体**：二课响应客户端直接收，后端**从不接触**。
4. **不生成 `client_local` 参数**：GPS、扫码时间戳、`codeTime`、`gpsCode` **一律不代填、不伪造、不给默认值**。
5. **不判 `code=5`**：token 失效由客户端判定（#63 §二 表 B），后端不为它定义错误码。
6. **不驱动流程**：多跳只声明「先后 + 取值路径」，**不代替客户端做控制流**（无重试、无分支、无条件跳转）。
7. **不中转文件**：multipart 的字节流客户端直传二课。

## 五、失败语义与幂等（哪些能定、哪些定不了）

### 能定的（写进契约）

1. **幂等由客户端 + 二课侧承担，后端不承接**。理由：后端不代发、不重试，就没有「后端层面的重复提交」这回事；重复是客户端行为，只有客户端知道「我刚发过一次」。
2. **`code=5` 后的重试**：客户端拿到 token 失效后应重新取 token 再发，**不是**让后端重发。
3. **网络失败的本地重试策略**：**不在本仓规定**（后端观测不到），留客户端自定。

### 定不了的（留 fog，不硬编）

| 问题 | 为什么定不了 |
| --- | --- |
| 重复扫码签到，二课是**报错**还是**幂等成功**？ | 离线样本只有请求参数，**看不到行为**。必须真账号验 |
| 签到二维码 `qrCodeTimestamp` 的**有效时长**是多少？ | 同上，产物里无 |
| 报名重复提交，二课返回什么码？ | 同上 |
| 签退超时后能否补签？ | 同上 |

**这些不写进契约，写成 Spec 的「待验证项」**——按 #51 的 pending 四层，归第 ④ 层「需实测」。

## 六、留给 Spec 的阻塞项

1. **活动发布/编辑类配方是否给学生**：`ActivityEdit`/`updateActivity`/`saveActivity` 是组织者能力。若只给组织者，则「按角色下发不同配方集」需要一个角色判定口径——**这不在本票范围**（涉及管理台与角色模型，#59 已把管理台 UI 排除，但配方按角色分发是后端的事）。**转 Spec 或新开一票。**
2. **多跳是否真的需要**：签到系列是否需要「先取 memberId」取决于二课真实行为（可能 `actId` 就够）。**须真账号验。**
3. **`contentType: form` 之外还有没有别的编码**：172 全是 form/multipart，但真实请求可能带额外 header（如 `pu-version` 等 7 个设备头只挂 `getGsonApi`、Rx 侧不带）。**配方是否需要声明设备头**——留 Spec 判。
