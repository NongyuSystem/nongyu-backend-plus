### 1.2 关键判断：它含用户/会话维度，不能硬编码

三条独立证据：

1. **形态证据**：`dizhi`(600 位) / `o`(78 位) / `w1`(150 位) / `rul`(300 位) / `h`(78 位) 是超大纯数字串，远超任何正常参数长度，是典型的**服务端加密或签名后回填**形态；纯时间戳或 id 不会这么长。[来源: 同文件:19-20]
2. **孤立证据**：对 `@OLD/packages/nongyu-tool-jiaowu/core/` 全量 grep `rig=` / `bh=` / `&rig` / `&bh`，**只在 `planInfo.ts` 一处命中，其他模块零命中**。若是通用常量（如校区 id），其他查询模块理应复用。[来源: 本条为实测 grep，命令见下「验证」]
3. **无解密路径**：整个 `core/` 里唯一的解密函数是 `decryptCasData`（用于 CAS 响应体 AES 解密）[来源: `@OLD/packages/nongyu-tool-jiaowu/core/login/cas.ts:132-169`]；**没有任何针对 `dizhi/rul/h` 这类参数的解密或生成代码**，说明旧实现只是**原样透传**从页面抓到的值。

**结论（可施工）**：`PLAN_FIXED_PARAMS` **不能做成静态常量**。Go 侧必须先 `GET` 一次 `jjihua.asp?title_id1=1` 拿到页面，从 HTML 里提取这些隐藏域（它们在页面内应是以 `<input type=hidden>` 或表单 query 的形式存在），再拼第二次请求。**这一条推翻了我原先写在票 #31 里的假设「能否用静态常量替代」——答案是不能。**

### 1.3 尚未查清

- 这些隐藏域**具体以什么 HTML 形态出现在页面上**（`<input type=hidden name=dizhi>`？还是页面内嵌的 `location.href`？）——需要登录后的真实页面才能确认，属真账号验证范围（见票 #33）。
- `rig` / `bh` 是否等于学号或其哈希——仓内无任何线索，**不推测**。若是学号维度，则抓取必须按用户做、不可跨用户复用（这点对缓存键也有影响）。

## 二、`progressInfo` 的「行宽启发式」与脆断点

### 2.1 精确判据（不是 `=== 7`）

选表：对每张表用关键字 `["课程性质","应修学分","已修学分","学分差","可结转学分","分段完成进度"]` 给**前 3 行**打分，取分数最高且 > 0 的表 [来源: `@OLD/packages/nongyu-tool-jiaowu/core/extractor/progressInfoExtractor.ts:85-119`]。

行处理：

| 步骤 | 精确条件 | 来源 |
| --- | --- | --- |
| 行进入候选 | `row.length >= 5` | `progressInfoExtractor.ts:58` |
| 过滤表头行 | 任一分格含 `课程性质` 或 `应修` 即丢弃 | 同文件:59 |
| **偏移判据** | **`row.length > 6` → offset = 1，否则 0** | 同文件:64 |
| 字段映射 | `type=row[offset]`, `required=row[offset+1]`, `earned=row[offset+2]`, `diff=row[offset+3]`, `transfer=row[offset+4]`, `progress=row[offset+5]` | 同文件:66-73 |
| 行有效性 | `type && (required \|\| earned)` | 同文件:75 |

（源码注释原文：「含 rowspan 分类标签的行有 7 列，不含的 6 列，合计行中 colspan=2 后也有 6 列」[来源: 同文件:58 行内注释]）

### 2.2 会脆断的具体情形

由于判据是 `> 6`（而非 `=== 7`），**任何 ≥ 7 列的行都会被当成「有分类标签」而左移一格**：

1. **教务新增一列**（例如把「分段完成进度」拆成「分段完成进度」+「进度说明」，变成 8 列）→ `row.length > 6` 成立，offset=1，于是 `type` 取到真实的数据列（应修学分），`required` 取到已修学分……**整行右错一格**，`progress` 落到不存在的下标取到 `undefined`（TS）→ Go 里是空串。
2. **rowspan 少一格**：某行的分类标签被上一行 rowspan 覆盖（该行只有 6 格但仍属分类组）→ 判据取 offset=0 → `type` 取到 `required` 的值（数字当分类名）。
3. **合计行**：注释说合计行 colspan=2 后也是 6 列，但若教务改了合计行的 colspan，同样落进 7 列分支而错位。

三个问题的共同点：**错位不抛错、不告警，产出的 `ProgressItem` 仍满足 `type && (required||earned)` 有效性门槛**，会被当作正常数据缓存住。

### 2.3 Go 侧避免脆断的做法

不要把「列数」当分类标签的信号。改为：

1. **用表头关键字定位列**（与 score/exam 一致的做法），而不是下标偏移。表头行已被 `课程性质`/`应修` 过滤规则单独识别，可直接对表头做 `findIdx` 得到每个字段的列号。
2. **分类标签列单独判定**：分类标签的语义特征是「该格文本命中已知分类集合」（如 `必修` / `选修` / `限选` / `公选` / `任选` / `合计`），用文本判定 + 与该行数值列的类型差异（非纯数字）双重确认，而不是靠宽度。
3. **形状校验兜底**：`required/earned/diff/transfer` 应是数值形态（允许 `--`、空）；若某字段取到非数值文本，判 `parse_failed` 而不是静默下发——这与地图里「解析失败不写缓存」的口径一致。

## 三、`examInfo` 的 `examTime` 散文要不要结构化

### 3.1 真实形态（`@example` 一手样本）

```text
【考试时间：2026-7-2】 第18周-星期4-上午(09:00—11:00)   请08:45到考场
【考试时间：2026-7-6】 第19周-星期1-晚上(19:00—21:00)   请18:45到考场
```

[来源: `@OLD/packages/nongyu-tool-jiaowu/core/jiaowu/examInfo.ts:36-50`（`@example` 块）]

可抽出的结构化成分：

| 成分 | 正则片段 | 备注 |
| --- | --- | --- |
| 日期 | `【考试时间：(\d{4}-\d{1,2}-\d{1,2})】` | 月/日为**非补零**（`2026-7-2`） |
| 周次 | `第(\d+)周` | |
| 星期 | `星期(\d)` | 阿拉伯数字，非「一/二」 |
| 时段名 | `-(上午\|下午\|晚上)\(` | |
| 起止时刻 | `\((\d{2}:\d{2})—(\d{2}:\d{2})\)` | 注意是**全角破折号 `—`** |
| 到场提醒 | `请(\d{2}:\d{2})到考场` | |

### 3.2 关键事实：extractor 不做任何清洗

`extractExamInfo` 对 `examTime` 只做 `pickCell(row, cols.examTime)` 原样取值，**没有任何正则解析或格式化** [来源: `@OLD/packages/nongyu-tool-jiaowu/core/extractor/examInfoExtractor.ts:66-78`]。行有效性判据是 `courseName || examTime` 任一非空 [来源: 同文件:77]。

### 3.3 结论（可施工）

- **下发原样字符串 + 可选的结构化字段**，但结构化字段必须是**可空**的（用 `omitempty` 或指针），不能填零值：因为存在只有部分成分的形态（例如教务只写 `【考试时间：2026-7-2】` 而无周次与时段），正则抽不出来时**省略该字段**而不是填 `""` 或 `0`。
- **不要**在解析失败时把 `examTime` 清空——原样串是唯一保真的信息，客户端与 Agent 都可能直接展示它。
- 注意 `—` 是全角破折号（U+2014），Go 侧正则该用 `\x{2014}` 或直接匹配字符串 `"—"`；用 ASCII `-` 会匹配失败。
- 月份/日期不补零（`2026-7-2` 而非 `2026-07-02`），解析时用 `\d{1,2}` 并自行补零。

## 四、`rankInfo` 的单对象语义

### 4.1 精确行为

- 选表：`extractSegments(table)` 后按关键字 `["排名","加权","学号","姓名","专业","年级"]` 给表头打分，取最高且 > 0 [来源: `@OLD/packages/nongyu-tool-jiaowu/core/extractor/rankInfoExtractor.ts:112-136`]。
- 列识别（`findIdx` = normalize 后**子串包含**，取第一个命中）[来源: 同文件:139-157]：

| 字段 | 关键字（按数组顺序） |
| --- | --- |
| `index` | `序` → `序号` |
| `campus` | `校区` |
| `college` | `系别` → `学院` |
| `major` | `专业` |
| `grade` | `年级` |
| `studentId` | `学号` |
| `name` | `姓名` |
| `className` | `班级` |
| `weightedScore` | `有效必修加权成绩` → `加权成绩` → `加权平均成绩` |
| `majorRank` | `专业排名` → `排名` |
| `status` | `在读情况` → `在读` |

- **单行返回**：`for` 循环从表头下一行开始，命中第一行「有数据」即 `return { result: item, success: true }`——**`return` 在循环体内**，不是循环结束后取值 [来源: 同文件:85-106]。
- 「有数据」判据：`studentId` / `name` / `weightedScore` / `majorRank` **四个字段任一非空** [来源: 同文件:95-100]。
- 无表或无有效行 → `{ result: null, success: false }` [来源: 同文件:50-59,105]。

### 4.2 风险

1. **多行会丢数据**：若该生页面上有分学期/多次排名（多行），现实现只取第一行，**其余静默丢弃**。仓内无该页面真实样本，无法确认是否单行——属真账号验证范围。
2. **`index` 列可能误命中**：`index` 用 `["序","序号"]` 且是子串匹配，`findIdx` 返回第一个命中的列。而 `weightedScore` 的 `"加权成绩"` 不会命中 `序`，但要注意表头若含「序号」与其他含「序」的列，会取到靠前的那列。
3. **`majorRank` 的 `"排名"` 是极宽关键字**：任何含「排名」的列（如「班级排名」「年级排名」）都可能被先命中，取决于表头列序。

### 4.3 结论（可施工）

- **保持单对象 `RankItem`**（与旧契约一致，客户端已按单对象消费），但 Go 侧**内部**应先把所有有效行都解析出来，再取第一行返回，并在命中多行时**记一条审计/日志**（这样上游若真的改成多行，我们能发现而不是静默丢弃）。
- 列识别改为**最长关键字优先 + 全等优先**，避免 `"排名"` 抢先命中：即先用 `专业排名` 找，找不到再用 `排名`，且优先精确等于。
- `weightedScore` 同理：`有效必修加权成绩` > `加权平均成绩` > `加权成绩` 顺序尝试。
