## 一、落点决定（合拢八张票的结论，2026-11-12）

1. **四个顶层业务域**（不是六个）：`content/`（帖子 + 公告两个子域）、`message/`（通知 + 内部信）、`track/`（用户行为埋点）、`admin/` 不设域（管理台只是**同一批域的路由前缀 + 中间件**，不新增域）。理由：域按**业务能力**切，不按「谁调用」切；`/admin/*` 是入口差异，不是模型差异。
2. **`content/` 是父包 + 两个子域**（与 `identity/`、`school/` 同构）：`content/post/`、`content/announcement/`。父包只放跨子域共享契约（错误码、`board` 枚举、内容可见性判定入口）。**两个子域之间不互相 import**。
3. **`platform` 只新增 1 个接口**：`ObjectStore`（#53 已定方法集）。**埋点写入与消息写入不新增 platform 接口**——它们是**本仓自己拥有的业务数据**（PG 表），不是外部能力；直接走各域自己的 repo（与 `identity/` 读写自己表的方式一致）。这一点是本草图最需要维护者点头的判断。
4. **通知派生放装配层薄单元** `app/notify/`（#48 Q2 已定），**不新建 `internal/notification` 域**。
5. **`/admin/*` 只加中间件，不加域**：复用 #46 已定的 `AdminOnly` 薄封装；管理台端点写在各域自己的 handler 里，挂在 `/admin/<域>/...` 前缀下。
6. **中间件链固定**（#46 Q5）：`RequestID → NY1(适用时) → 鉴权 → AdminOnly(仅 /admin) → 限流`。
7. **公开读清单另立**（#46 Q1）：`publicReadablePaths` 与既有 `publicPaths` 并列，**共用同一个 `IsPublicPath` 判定**。

## 二、包依赖图

```
                        cmd/server/main.go
                                │
                                ▼
                       internal/app  (composition root)
    ┌──────────┬──────────┬───────┴───────┬──────────────┬──────────┐
    │          │          │               │              │          │
    ▼          ▼          ▼               ▼              ▼          ▼
 config     server    content/        message/        track/    platform
                      ├── post/                                         ▲
                      └── announcement/                                  │
                            │              │              │              │
                            └──────────────┴──────────────┴──────────────┘
                                    只依赖接口（README 第 2 条）

        internal/app/notify/   ← 装配层薄单元：跨域编排，不 import 任何域的内部
```

**关键变化**：新增 `content/`（父包 + 2 子域）、`message/`、`track/` 三个业务域，以及装配层的 `app/notify/`。

**约束核对**（与 `README.md:42-48` 逐条对照）：

| # | 约束 | 本草图如何满足 |
| --- | --- | --- |
| 1 | 业务域之间不互相 import | `content/post` 与 `content/announcement` 互不 import；两者都不 import `message`；跨域写消息**只经 `app/notify`**。`track` 不被任何域 import。 |
| 2 | 只依赖 `internal/platform` 接口，不 import 数据库驱动／S3 SDK | 全部域只见 `platform.*` 接口类型；S3 SDK **只允许 `platform/objectstore/`** import（#53 Q5，可用 `go list -deps` 断言）。 |
| 3 | 进程无状态 | 所有状态在 PG／Redis／对象存储；**通知的有界队列在进程内但允许丢**（#48 Q3），不构成状态依赖——重启丢失可接受。 |
| 4 | 域内自带 handler/service/repo 接口，存储实现放 platform 或其子包 | 每个域自带 `handler.go`／`service.go`／`repo.go`（**repo 是接口**）；PG 实现放 `platform/pgstore/`（沿用既有做法）。 |
| 5 | 不提前建 `pkg/utils`、`common` 垃圾场包 | 不新建任何顶层 `pkg/`；共享错误码放各父包（`content/`、`message/`）。 |

## 三、`internal/platform` 增量（**只 1 个新接口**）

```go
// ObjectStore 是对象存储的外部能力接缝（#53 决议）。
// 只允许 platform/objectstore/ 的实现 import S3 SDK。
type ObjectStore interface {
    Put(ctx context.Context, key string, r io.Reader, size int64, contentType string) (ObjectInfo, error)
    PresignGet(ctx context.Context, key string, ttl time.Duration) (string, error)
    Delete(ctx context.Context, key string) error
    Stat(ctx context.Context, key string) (ObjectInfo, error)
}

type ObjectInfo struct {
    Key         string
    Size        int64
    ContentType string
    ETag        string
}
```

**明确不新增的接口**（这是最需要点头的一处判断）：

| 能力 | 为什么不进 platform | 走哪里 |
| --- | --- | --- |
| 埋点写入 | `track_event` 是**本仓自己的 PG 表**，不是外部系统。给它开 platform 接口等于把「一张自己的表」抬成外部能力，会让 `track` 域失去对自己数据的直接掌控。 | `track` 域自己的 `repo.go`（接口）＋ `platform/pgstore/`（实现） |
| 消息写入 | 同上：`message` 表是本仓数据。 | `message` 域自己的 `repo.go` |
| 通知派生 | 它是**跨域编排**，不是外部能力。 | `app/notify/` |

**复用既有、不新增**：`platform.Clock`（预签名 TTL 计算与测试注入）、`platform.RedisCache`（帖子列表缓存，`GET /posts` 与 `/posts/:id`）、`platform.AuditStore`（`notification.emit`／`notification.dropped` 等 action）、`platform.LockBackend`（若将来需要上传去重）、`platform.Store`（**不用于本次六功能**，维持骨架期定位）。

## 四、四个域的包形状

```
internal/
├── content/                          ← 新：内容域（父包只放共享契约）
│   ├── doc.go
│   ├── content.go                    共享：错误码、Board 枚举(feedback/courtyard)、可见性判定入口
│   │
│   ├── post/                         ← 子域 1：帖子
│   │   ├── doc.go
│   │   ├── post.go                   帖子实体、附件引用（只存 object key，不存 URL）
│   │   ├── service.go                发帖/回复/点赞/收藏/24h 编辑/软删
│   │   ├── repo.go                   接口（PG 实现放 platform/pgstore/）

│       ├── repo.go
│       └── handler.go                /announcements*、/admin/announcements*

│   ├── service.go                    写投递行(upsert 累加)、已读、软删、未读数

│   └── handler.go                    /messages*（POST 仅内部信）
│
├── track/                            ← 新：用户行为埋点域

│   ├── event.go                      事件枚举(7 种)、公共字段、props 校验与脱敏
│   ├── buffer.go                     有界缓冲 + 后台批量写 + 满则丢弃计数
│   ├── service.go
│   ├── repo.go
│   └── handler.go                    POST /track/events、GET /track/events/summary
│
├── app/
│   ├── app.go                        装配：注入 Capabilities（新增 ObjectStore 字段）
│   └── notify/                       ← 新：装配层薄单元（跨域编排，不是业务域）
│       ├── notify.go                 5 个触发点 → 收件人集合 → 调 message 写入口
```

**`content/` 父包为什么值得存在**：`post` 与 `announcement` 都要回答「这条内容对当前用户可见吗」，且都用 `StudentBriefReader` 做受众过滤。把它放父包，避免两个子域各写一套（README 第 1 条允许父包放共享契约）。

## 五、路由与中间件挂点

```
/healthz, /status                    ← 既有，公开且限流豁免（限流仍只豁免 /healthz）

公开读（进 publicReadablePaths，与 publicPaths 并列、共用 IsPublicPath）：
  GET /announcements
  GET /announcements/:id
  GET /announcements/latest
  GET /posts
  GET /posts/:id

需农屿会话：
  POST   /posts                    回复/发帖/点赞/收藏/编辑/删除
  POST   /messages                 仅内部信
  GET    /messages, /messages/unread-count
  PATCH  /messages/:id/read
  POST   /messages/read-all
  DELETE /messages/:id
  POST   /track/events             埋点上报（NY1 签名适用，App 端）
  GET    /track/events/summary     仅管理端可读

管理端（新增 AdminOnly 中间件，scope=admin 且 role>=1；敏感操作 role>=2）：
  /admin/announcements    CRUD
  /admin/posts            管理动作
  /admin/track/summary    或复用上面
```

中间件链（#46 Q5 已定，此处只画挂点）：

```
RequestID → NY1(适用时：App 业务与埋点；/admin/* 不签) → 鉴权(会话) → AdminOnly(仅 /admin) → 限流
```

**与既有设施的关系**：不新增 `RequestIDMiddleware`／限流实现；`publicReadablePaths` 是**新增的第二张清单**，但**判定入口仍只有 `IsPublicPath`**（#46 Q1 的核心约束）。

## 六、数据流

```
① 发帖（含附件）
客户端 ──POST /posts (multipart, ≤9 张/5MB/四格式)──► content/post/handler
   └─► post/service 校验体积与格式（MaxBytesReader 硬限）
        ├─► platform.ObjectStore.Put(key=posts/{yyyy}/{MM}/{uuid}.{ext})   ← 流式，不落盘
        └─► post/repo 写入帖子行（只存 object key）
              └─► app/notify （为 4 个触发点之一准备，若适用）

② 读帖
客户端 ──GET /posts/:id──► post/handler
   └─► 先查缓存(RedisCache) → 未命中查 repo
        └─► 对每个附件 key 调 platform.ObjectStore.PresignGet(ttl 短)
             （鉴权通过才签发；软删后已签发 URL 在 TTL 内仍可访问 —— 已接受的代价）

③ 通知派生（装配层，异步旁路）
content/post 或 content/announcement 提交成功后
   └─► app/notify.Enqueue(动作事件)          ← 非阻塞；队列满则丢弃 + dropped++
        └─► 后台协程：算收件人（排除自己）→ message/service.Upsert(幂等键)
              └─► 失败只记日志 + dropped++，绝不回滚主业务

④ 埋点上报
客户端 ──POST /track/events(批量 1~100)──► track/handler
   └─► 逐条校验 + 脱敏(顶层白名单 + props 敏感键剔除 + 4KB 截断)
        └─► track/buffer 有界缓冲 → 后台批量写 PG track_event
             （满则丢弃 + dropped++，不返 503）
```

## 七、测试接缝（为 Spec 的两层做准备）

| 层 | 需要真实外部依赖？ | 怎么测 |
| --- | --- | --- |
| 纯逻辑（可见性判定、受众过滤、幂等键组装、脱敏规则、props 校验） | **不需要** | 纯函数单测，无 IO |
| 域 service（帖子/公告/消息业务规则） | 只需 **repo 接口的假实现** | 内存 fake repo，不碰 PG |
| PG 仓储行为（部分唯一索引 upsert、未读数 count、软删语义） | **需要真实 PG** | 集成测试（仓内已有 pgx 测试做法） |
| 对象存储行为（Put/PresignGet/Delete） | **需要真实 MinIO** | 集成测试；**MinIO presigned 行为本身仍是 #53 Q6 的 Spec pending 项** |
| 通知派生的异步与丢弃 | 不需要外部依赖 | 用可控队列 + 断言 dropped 计数 |
| 中间件链（公开读 / AdminOnly / NY1 分层） | 不需要 | `httptest` 打路由，断言状态码 |

**明确结论**：本六功能里**只有两处必须有真实外部依赖**——PG 的 `(recipient_id,kind,source_domain,source_object_id)` 部分唯一索引 upsert 行为，以及 MinIO 的预签名读写。其余全部可用纯逻辑或 fake 覆盖。

## 八、需要维护者点头的三处判断

1. **埋点与消息不新增 platform 接口**（第一节第 3 条）：它们是本仓自有数据，做成 platform 接口会让域失去对自己数据的掌控。**这是本草图与你预期最可能不一致的一处。**
2. **`content/` 父包 + 两子域**（而非两个顶层域）：理由是共享可见性判定与 `StudentBriefReader` 用法。
3. **`admin/` 不设域**（只加中间件 + 路由前缀）：避免为「同一批模型的管理入口」复制一套域。

## 九、本草图不做的事

- 不产出可运行代码、不建表、不改路由（wayfinder 只产决策与形状）。
- 不重开任何已关决议的语义（八张票的结论原样采用）。
- 不替代 Spec：字段名、索引、TTL 值、队列参数、`audit_log.action` 完整取值表仍是 [#51](https://github.com/NongyuSystem/nongyu-backend-plus/issues/51) 的事。
