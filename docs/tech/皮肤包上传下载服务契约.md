# 皮肤包上传 / 下载服务契约（issue #53）

> 服务端实现：`internal/skin/`，迁移 `migrations/0007_skins.sql`。
> 客户端契约唯一真源：`nongyu-app-plus` 的 `skin/SkinPack.kt`（清单与完整性）、
> `skin/SkinManifestParser.kt`（清单解析）、`skin/SkinStore.kt`（落盘与指针），
> 以及 ADR-0003 / 0004 / 0006。本文件只记录**两端之间的 HTTP 契约**与
> 服务端落点，不重述 ADR 的决策理由。

## 1. 定位

补上客户端 #53「皮肤包下载器」的服务端对端：B 端（管理台）上传皮肤包，
App 在**首帧之后**拉目录、下载包体、校验、落盘。服务端只负责
「存 + 下发 + 全局单指针」，**不参与启动路径**（ADR-0006）。

两层存储（维护者指定 MinIO + 数据库）：

| 数据 | 落点 | 说明 |
| --- | --- | --- |
| 包体 zip | 对象存储 MinIO，key `skins/{packId}/{version}.zip` | 配 `MINIO_ENDPOINT` 即 MinIO，否则回落内存实现（仅本地开发，显眼 WARN） |
| 元数据 + 全局单指针 | Postgres `skin_packs` / `skin_current` | 配 `DATABASE_URL` 即 PG，否则回落内存实现；与既有五域共用同一切换口径 |

包体**不进数据库**；数据库里的 `manifest_json` 是包内 `manifest.json` 的
**原文**（TEXT 而非 JSONB），原样透传给客户端，不重新序列化——避免改动
字段顺序或整包签名所依赖的内容。

## 2. 包体格式（与客户端 `SkinPack` 逐字段对齐）

一个 zip，根目录至少含：

```
manifest.json                  ← 清单（唯一）
icons/...、fonts/...            ← 清单 integrity.entries 声明的资源文件
```

`manifest.json`（新结构，ADR-0003）：

```json
{
  "packId": "default-green",
  "schemaVersion": 1,
  "minAppVersion": 1,
  "displayName": "农屿默认绿",
  "payload": {
    "iconStrokes": { "home": 0.8 },
    "fontFileName": "fonts/nongyu.ttf"
  },
  "integrity": {
    "entries": [ { "path": "icons/home.png", "sha256": "<64位小写hex>" } ],
    "signature": "<base64：B 端对规范化摘要的签名>"
  }
}
```

约束（服务端 `ValidateManifest` / `VerifyPack` 逐条对齐客户端解析器）：

- 6 项必填：`packId`、`schemaVersion`、`minAppVersion`、`displayName`、
  `payload`、`integrity`；`integrity.signature` 非空（客户端缺签名整包拒绝）。
- `schemaVersion` 主版本 ≤ `SupportedSchemaMajor`（=1，与客户端常量同步）。
- `integrity.entries` 非空、路径合法、sha256 为 64 位小写 hex、路径不重复。
- 扩展名白名单：`json / ttf / otf / ttc / png / webp / jpg / jpeg`；
  挡绝对路径、`..` 目录穿越、目录条目、无扩展名、禁用可执行扩展名
  （`dex/jar/so/apk/aab/class/odex/oat/vdex/dylib/sh/bat/exe`）。
- 包内除 `manifest.json` 外的文件**必须**都在 entries 里（挡夹带）；
  每个 entry **必须**在包里存在且 sha256 一致（挡半成品 / 篡改）。
- `fontFileName` 若声明，须是合法相对路径且出现在 entries 里。
- zip 本体 ≤ 20 MiB、解压后总量 ≤ 64 MiB、文件数 ≤ 512（zip 炸弹防护）。

**服务端不校验整包签名的真伪。** 签名是 B 端私钥对规范化摘要签的，信任根
（公钥）在客户端；服务端只把它原样存下来随包下发。理由见
`docs/research/skin-decoupling-routes.md`：传输只解「谁能取」，不解
「是不是官方包」，完整性最终由应用侧（客户端 `SkinPackIntegrity.verify`）判。

## 3. HTTP 契约

成功响应是**裸业务结构体**（与本仓既有端点一致），错误是
`{"code":"...","message":"..."}`（apperr 统一）。

### 3.1 App 侧（只读，全局单指针）

免用户会话（已加入 `server.publicReadablePaths` 的 `/skins`，仅 GET/HEAD），
但仍需 NY1 请求签名（`APP_SIGNING_KEYS` 装配时）——客户端首帧后拉取时可能
尚未登录，但必须证明来自持有密钥的客户端。

| method | path | 说明 |
| --- | --- | --- |
| GET | `/skins/current` | **目录接口**：当前生效皮肤 |
| GET | `/skins/:packId/:version` | 单个包详情 |
| GET | `/skins/:packId/:version/pack` | 包体下载（后端流式代理对象存储） |

`GET /skins/current` 响应：

```json
{
  "hasPack": true,
  "packId": "default-green",
  "version": "1.0.0",
  "schemaVersion": 1,
  "minAppVersion": 1,
  "displayName": "农屿默认绿",
  "packSha256": "<整个 zip 的 sha256>",
  "packSize": 12345,
  "manifest": { ... },            // 包内 manifest.json 原文
  "downloadUrl": "/skins/default-green/1.0.0/pack",
  "updatedAt": "2026-11-16T..."
}
```

**没有已激活包时**返回 `200 {"hasPack":false}`（不是 404）——「没有皮肤」
是正常态，客户端据此回落内置默认皮肤，绝不能编造一个包。

`GET .../pack` 响应：`Content-Type: application/zip`、
`Content-Disposition: attachment`、`X-Nongyu-Pack-Sha256: <整包 sha256>`，
body 为 zip 字节（流式，不落服务端内存）。客户端流程：拉目录 → 比对
`packSha256` → 下载 → 用 `manifest` 做逐文件 sha256 + 整包签名校验 →
结论 OK 才调 `SkinStore.install`。

### 3.2 管理端（B 端上传 / 发布 / 回滚）

挂在 `/admin/*`：`admin 会话（ScopeAdmin） + AdminOnly(role>=1)`，
NY1 签名豁免（浏览器拿不到 APK 密钥，见 `server/appsign.go` 的
`IsAppSignExempt`）。上传放这里而非 App 侧，是因为 NY1 中间件会把整个
body 读进内存且上限仅 1 MiB，而皮肤包可达 20 MiB。

| method | path | 说明 |
| --- | --- | --- |
| POST | `/admin/skins` | 上传（multipart/form-data） |
| GET | `/admin/skins?limit=50` | 已登记包列表 |
| POST | `/admin/skins/:packId/:version/activate` | 切换全局单指针（发布 / 回滚） |

`POST /admin/skins` 字段：

- `version`（必填）：版本目录名，对应客户端 `filesDir/skins/{packId}/{version}/`；
  只许字母数字与 `-_.`（与客户端 `isSafeSegment` 对齐）。
- `activate`（可选，`"true"` / `"1"`）：上传后立即把当前指针切到这版。
- `file`（必填）：zip 本体。

成功 `201` 返回登记后的 `CatalogEntry`（不含对象 key 等内部字段）。
失败：非法包 `400 validation_failed` / `schema_rejected`、超体积 `413
payload_too_large`、同版本重复 `409 conflict`、对象/元数据故障 `500`。

**版本不可变**：同一 `(packId, version)` 只能登记一次，重复上传返回
`409 conflict`。这是客户端「原子 rename + 当前指针 + 两套并存」的前提——
否则已缓存旧包的设备与新设备会看到同一版本号却是两套字节。

**回滚**不需要重新上传：`POST /admin/skins/{packId}/{oldVersion}/activate`
把指针指回上一版即可（ADR-0003）。

## 4. 失败不动已生效的包

与客户端「只在结论 OK 时调 `install`」对称，服务端上传顺序是：

1. `VerifyPack`（纯内存校验，任何一步失败不写对象存储）；
2. 写 MinIO.Put；
3. 写 PG 元数据（唯一约束挡重复）；
4. 仅当 `activate=true` 才切全局单指针。

第 3 步失败会尽力 `Delete` 掉刚写的对象（旁路，失败只记日志），避免留下
「库里查不到、MinIO 里却有个孤儿 zip」。任何失败都不改当前指针，
线上那套皮肤仍然可用。

## 6. 待实测 / 边界

- 真实 MinIO 的 `Get`（本次新增）未在仓内对真机实测；`PresignGet` 的
  「不校验存储侧身份」亦属既有未验证假设。接真实 MinIO 前应跑一次
  上传→下载往返。
- PG 路径的迁移 `0007_skins.sql` 由启动期 `platform.Migrate` 幂等执行；
  接真实库前应在 staging 跑一遍 `0007` 并确认外键与唯一约束生效。
- 整包签名的**产生**（B 端签名工具 / 密钥管理）不在本服务范围；本服务只
  保证签名非空并原样透传。
