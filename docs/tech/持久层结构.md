# 持久层结构：Postgres / 日志 / KV 的分工

本文回答「哪类数据放哪里、为什么」，以及本仓目前的落地状态。写于 2026-11-08。

## 一、三层分工

| 层 | 用什么 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| **结构化真相** | Postgres 18（本机 `127.0.0.1:5432`，独立库 `nongyu`） | 审计流水 `audit_log`；将来的业务表（用户偏好、提醒规则等） | 票据、缓存、日志原文 |
| **日志检索** | Elasticsearch 9.1.4 + Kibana（已运行） | 运行日志的检索与可视化 | **业务真相**（无事务、写入可能丢、重建贵） |
| **KV / 缓存** | Redis 8.10（`my-redis`） | 票据、缓存、幂等锁、限流计数、状态上报 | 需要长期留存的审计数据 |

## 二、关键决策与理由

### 1. 应用**不直连 ES**

应用只把日志写到 stdout，由采集器（Filebeat / Vector / Fluent Bit）送进 ES。

理由：双写（PG 与 ES 各写一份）会把一致性问题引入业务代码；而日志本身是可丢的旁路数据，天然适合「先落 stdout、再被采集」。将来接入采集器时，应用代码零改动。

### 2. 票据**不进** PG

票据是短期凭据（9 天窗口）、高频读写、需要原子过期语义——Redis 更合适。放进 PG 只会扩大泄漏面并拖慢登录路径。

### 3. KV 不新增

Redis 就是 KV。etcd / Consul 只在「配置中心 / 服务发现 / 强一致选主」场景才值得引入，本项目当前都不需要。

### 4. 审计是**旁路**

审计写入失败、缓冲区满导致丢弃，都**不允许影响业务**。实现上：
- `Append` 只做非阻塞入缓冲，满则丢弃并计数（`Dropped()`）；
- 后台按 `FlushPeriod` 批量 `INSERT`，一次提交多条；
- 关停前 `Flush` 一次，并打印丢弃计数。

这是明确的取舍：**宁可丢审计，也不能因为审计库慢让用户登录失败**。

## 三、审计表

```sql
audit_log (
  id          bigserial primary key,
  request_id  text        -- 审计流水号（一次请求一个，与 X-Request-Id 响应头一致）
  user_id     text        -- 已认证身份
  action      text        -- login / logout / address / fetch / captcha / login_accel / renew
  target      text        -- 逻辑目标名：jiaowu / auth / webvpn
  result      text        -- ok / target_denied / outbound_error / captcha_error / ...
  occurred_at timestamptz -- 事件发生时刻（应用时钟）
  created_at  timestamptz -- 入库时刻（数据库时钟）
)
```

索引：`(user_id, occurred_at desc)`、`(action, occurred_at desc)`、`(request_id)`。

**铁律**：表里只有标识性字段。绝不写票据、密文、验证码、上游响应体——审计表不能成为泄漏面。

流水号由 `server.RequestIDMiddleware` 生成（优先复用调用方的 `X-Request-Id`），写入 context 与响应头，业务域通过 `school.CtxRequestID` 读取。**这一次请求的多个动作因此可以在表里串起来**——这正是 Spec 里「审计流水号机制待定」那一项的落地。

## 四、迁移

迁移脚本在 [`migrations/`](../migrations/)，按序号命名，幂等（`IF NOT EXISTS`）。

```powershell
$env:PGPASSWORD="<密码>"
psql -h 127.0.0.1 -p 5432 -U postgres -d nongyu -f migrations/0001_audit_log.sql
```

建库（一次性）：
```powershell
psql -h 127.0.0.1 -p 5432 -U postgres -d postgres -c "CREATE DATABASE nongyu;"
```

## 五、配置

| 环境变量 | 说明 |
| --- | --- |
| `DATABASE_URL` | `postgres://user:pass@host:port/db?sslmode=disable`；为空则审计只写 stdout |

**注意**：这台 PG 是**共享实例**（已有 16 个其它项目的库），本项目的所有表都在独立库 `nongyu` 内，不碰任何其他库。

## 六、验证方式

```powershell
$env:DATABASE_URL="postgres://postgres:<密码>@127.0.0.1:5432/nongyu?sslmode=disable"
go test -count=1 ./internal/platform/... -run TestPGAudit
```

端到端验证（真实 HTTP → 真实 PG）：
```powershell
# 1. 起服务
$env:ADDR=":18081"; $env:APP_ENV="dev"; $env:AUTH_KEY="e2e-secret-key"
go run ./cmd/server
# 2. 用 tools/gentoken 生成 token 后请求业务端点
go run ./tools/gentoken -key "e2e-secret-key" -user "e2e-alice"
# 3. 查库应能看到对应 request_id 的记录
```

实测结论：`/school/address` 的值请求落库为 `user_id=e2e-alice, action=address, target=jiaowu, result=ok`，且 `request_id` 与响应头 `X-Request-Id` 完全一致。

## 七、没做的

- **日志采集器**：应用只写 stdout，采集器（Filebeat 等）尚未部署。ES 目前没接收本项目日志。
- **业务表**：除审计外尚无业务数据需要落 PG。
- **迁移工具链**：目前用手工 `psql -f`，没有 golang-migrate / goose。表数量变多时再引入。
- **审计保留策略**：没有分区或定期清理。数据量大后需要按 `occurred_at` 分区或归档。
