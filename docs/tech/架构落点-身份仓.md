## 一、三块 vs 一个域两个子域

维护者说的是「2~3 块功能」：**鉴权**、**登录**、**用户**。

落点采用 `internal/identity/` 一个业务域、两个子域（与 `school/` 同构）：

| 用户口语 | 落到哪 | 理由 |
| --- | --- | --- |
| 登录（四种方式、无感注册） | `identity/login/` | 登录是在「确立身份」 |
| 鉴权（会话校验、role 判定） | `identity/session/` | 鉴权是登录的延伸，共用同一套令牌 |
| 用户（用户信息 / 画像 detail） | `identity/user/` | 画像是「被展示的数据」，与凭据分离 |

父包 `identity/` 只放**跨子域共享的契约**：统一错误码（沿用 `school.Code` 那套风格）、身份上下文键、role 枚举。

## 四、会话可吊销（维护者已定）

令牌**改为可吊销**，代价是每次鉴权多一次会话查询。具体形状：

- 令牌本身只带 `session_id` 与签名（不携带权限判断所需的全部信息）；
- 中间件验签后，**查会话存储**确认：未过期、未吊销、`scope` 匹配、`device_id` 匹配（App 侧单设备）；
- 会话存 **Redis**（已有能力），key 形如 `identity:session:<session_id>`，TTL 与会话过期一致；
- 吊销＝删除该 key（并可选写一条「已吊销」墓碑防止令牌被重放，视需求再定）。

取舍已接受：**多一跳 Redis 读**换取「能踢人」。命中率靠会话 TTL 与 Redis 前置缓存保持。

**复用已有的**：`Clock`、`AuditStore`、`RateLimiter`、`RequestID`。

### 关于 `StudentBriefReader`（域间读取画像的约定）

维护者已定：其它域读画像**走窄接口，不走裸仓储、也不直接依赖 Service**。

- 接口定义在 `platform`，**只暴露最小字段集**（姓名、学院、专业、班级、年级）——身份证、QQ、头像等一律不出现在这个接口里。这是**结构性**的最小暴露，而不是靠调用方自觉。
- 实现放在 `identity/user`，在 `app` 里注册。其它域只 import `platform`，不违反「业务域不互相 import」。
- 需要新字段时，**新增一个专门的窄接口**，而不是把这个接口撑大——避免它退化成「读整张画像表」的通用口子。
- 若某域需要「写画像」，同样按此办理（目前没有这种需求）。

**不采用的方案**：直接依赖 `identity/user.Service`（打破业务域隔离，且拿到完整画像）；事件同步副本（对本项目过重）。

## 六、数据库表（Postgres，库 `nongyu`）

沿用已有迁移风格（`migrations/` 下按序号命名、幂等）。只列形状，不写 DDL。

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `users` | `id`, `student_no`(唯一), `status`, `role`, `created_at` | 一人一行；role 三档 0/1/2 |
| `user_profiles` | `user_id`(唯一), 学校档案字段, 农屿扩展字段, 身份证密文列 | 与 users 1:1 |
| `login_methods` | `id`, `user_id`, `kind`, `identifier`, `secret_ref`, `bound_at` | 四种方式各一行 |
| `sessions` | `id`, `user_id`, `scope`, `device_id`, `expires_at`, `revoked_at` | **权威存储；Redis 只做加速副本** |

**邮箱验证码不落 PG，存 Redis**（维护者已定）：

- key 形如 `identity:mailcode:<email>`，value 为验证码的哈希（**不存明文**），TTL = 验证码有效期；
- **TTL 同时也是一把「冷却锁」**：同一次发送写入后，在过期时间之内再请求发送一律拒绝（返回「请稍后再试」并给出剩余秒数），避免被当成邮件轰炸器；
- 校验成功即删除该 key（一次性；重放无效），校验失败累计次数超限也删除并要求重新获取；
- 该 key 天然带过期，无需清理任务；Redis 丢数据最多让在途验证码失效，用户重新获取即可——**这正是它适合放 Redis 的原因**。

**会话存储的双写**：Postgres 是权威（可审计、可追溯），Redis 是热路径副本。吊销时两边都写；Redis 丢数据可从 PG 重建。

## 七、登录流程落点

```
POST /identity/login/{method}
        │
        ▼
  login.Service.Login(method, credentials)
        │
        ├─ school    ──▶ platform.SchoolAuthenticator 确认学号
        │                 └─ 成功后：写画像（学校档案）＋ 密码镜像
        ├─ password  ──▶ 查 login_methods → 比对密码镜像 → 学号已知
        ├─ mailcode  ──▶ 验码（SMTP 发）→ 查 login_methods → 学号已知
        └─ idcard    ──▶ 查 users 按学号 → 比对画像里的后四位与首字母
                          ★ 身份证号来自画像（服务端存），不来自输入
        │
        ▼
  用户存在？ ─ 否 ─▶ 非 school 方式：返回「需先完成学校认证」
                    school 方式：建用户（无感注册）＋ 绑方式
        │
        ▼
  检查 status 未被禁用
        │
        ▼
  session.Service.Issue(user, scope, deviceID)  ← 吊销同 scope 的旧会话
        │
        ▼
  返回令牌 + 画像
```

## 九、结构已定格（2026-11-08 维护者拍板）

以下四条全部定了，落点图与表结构按此为准：

1. **业务域**：`internal/identity/` 一个域，下设 `login/`、`session/`、`user/`。
2. **令牌可吊销**：每次鉴权查会话存储，接受多一跳。
3. **邮箱验证码存 Redis**：TTL 即有效期，同时充当发送冷却锁；过期时间内重复请求发送一律拒绝。
4. **域间读画像走窄接口** `platform.StudentBriefReader`，不依赖 Service、不读裸仓储。

**仍缺的外部条件**（不阻塞落代码，只阻塞联调）：
