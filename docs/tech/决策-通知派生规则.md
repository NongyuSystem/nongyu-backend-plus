# 决议：通知与内部信的触发源与派生关系

> 来源：[决议：通知与内部信的触发源与派生关系（谁产生通知、幂等、去噪）](https://github.com/NongyuSystem/nongyu-backend-plus/issues/48)（wayfinder map #43 子票），2026-11-12 收口（HITL grilling，Q1~Q6 全 A）。
> 性质：**决策记录**，不是 Spec、不是实现。本票是跨域合拢票：承接 #44 / #49 / #55 三张已关票交办的派生规则。

## 前置（已锁，不在本票重开）

- **上游交办的触发点**：
  - [#44 公告](决策-公告域模型与作用域.md):22（Q4）——「公告**发布且对当前用户可见**」；收件人 = 受众条件集合；幂等键 `(announcement_id, user_id, publish_revision)`；**收件人计算 / 去噪 / 编排落点 / 失败语义全归 #48**。
  - [#49 帖子](决策-帖子域模型与契约.md):36-42（Q11）——**4 个触发点**：帖子被回复（帖主）／帖子被点赞（帖主）／评论被点赞（评论作者）／评论被回复（评论作者）；**无嵌套、深度 ≤ 2**；**收件人计算 / 幂等键 / 去噪合并 / 发给自己过滤 / 编排落点全归 #48**。
- **去重的物理承载已给**：[#55](决策-消息域模型.md):23（Q3）——`kind=通知` 建 `(recipient_id, kind, source_domain, source_object_id)` **部分唯一索引 + upsert 累加计数、保持未读**。本票只定**语义**，不重设计存储。
- **两个源域都不留通知位**：#49 Q6 **废弃** `notified_author` 行级布尔位与前台轮询；#44 Q3 **不自建已读/确认表**。→ 本票是唯一派生入口，无第二路径兜底。
- **架构硬约束**：`README.md:44` 业务域之间不互相 import，协作统一走 `internal/app` 装配层编排。
- **消息域写入面**：#55 Q5 定 `POST /messages` **仅供内部信**，**通知不接受外部直接建** → 通知只能由服务端内部路径产生。
- **审计口径**：[#46](决策-横切鉴权口径.md) Q3 —— `action` 用 `<域>.<动作>`、一次动作一条、对象记 `target`（`<域>:<id>`）、只记标识性字段。
- **旁路先例**：`docs/tech/持久层结构.md`:36-43 —— 审计是旁路（非阻塞入缓冲、满则丢弃计数、批量 flush，「宁可丢审计，也不能让业务失败」）。

## 决议（Q1~Q6 全 A）

**Q1 触发源清单 = 只保留 5 个**（公告发布 1 + 帖子 4）。**明确不做**三类：
1. **B 端管理操作（封禁／审核结果）**——#49 Q1 已定帖子域**不做审核态**，管理台也**无封禁能力**（#46 只定 role 三档 + admin 会话）→ **当前无来源可挂**。若将来要「操作通知」，须先新增该能力再回来加触发点。
2. **身份域登录异常**——属已关 map #19 的 effort，本图不碰（`README.md:3` 边界）。
3. **埋点不产生通知**——埋点是分析数据，与通知属不同层（`GLOSSARY.md` 三层互不替代）。

**Q2 编排落点 = `internal/app` 装配层薄编排单元**（如 `app/notify`），**不新建 `internal/notification` 业务域**。
- 理由：`README.md:44` 已把跨域协作指定给装配层；派生逻辑只是「算收件人 → 调消息域写入口」，**无独立状态与存储**，做成域会与既定分工重复。
- **帖子域／公告域不得 import 消息域**，只暴露「动作已发生」的窄接口由装配层消费。
- 若将来派生规则复杂到需要独立状态机，再考虑升格为域。

**Q3 同步/异步 = 异步旁路，绝不影响主业务**。
- 主业务（发帖／点赞／回复／公告发布）**先在自身事务里提交成功**；派生通知走**进程内异步**（有界队列 → 后台协程批量写）。
- **通知写入失败／队列满 → 丢弃并计数（`dropped`）**，**不抛错给用户、不回滚主业务**。
- 理由：通知是体验层，与审计同类旁路（参照 `持久层结构.md`:36-43）。
- **已记录的容忍度**：「帖子回复成功但通知没投递」可能发生；Spec 须写明该容忍度并暴露 `dropped` 计数以便观测。

**Q4 幂等键与去噪合并**：
- **公告**：`(announcement_id, user_id, publish_revision)` —— `publish_revision` 让「编辑重发」能再通知一次。
- **帖子/评论**：`(recipient_id, kind=通知, source_domain=post, source_object_id=<动作标识>)`，其中 `source_object_id` **包含动作与靶子**（如 `reply:1234`、`like:post:88`、`like:comment:99`）。使「同一帖被不同人点赞」**天然合并成同一收件人的一行**（recipient 与 source 相同）+ #55 Q3 的 upsert 累加计数。
- **本期不做时间窗**：同 source 反复触发即 `hits++` 并**重置为未读**，不按小时切窗。代价：长期被点赞的帖子只有「一条计数不断增长的通知」，看不到历史每次；若需时间窗则留 fog。
- 否决：不合并每次插一行（与 #55 Q3 的部分唯一索引直接冲突）；按 1 小时时间窗切分（需额外时间桶字段与索引，成本高于收益）。

**Q5 「发给自己过滤」= 双层**：
1. **编排层算收件人时就不把自己放进集合**（自赞／自回不产生通知）；
2. 消息域写入口按 **#55 D2** 再 fail-closed 拒一次。
- 理由：#55 D2 已定模型层拒；#48 作为收件人计算方**必须自己也过滤**，否则产生「算出来却被下游拒掉」的无谓写入与 `dropped` 计数失真。

**Q6 审计口径对齐 + Spec 交接**：
- **派生动作本身也记审计**：`notification.emit`（成功）／`notification.dropped`（丢弃），`target` 记 `<source_domain>:<source_object_id>`。
- **只记标识性字段**（沿 `持久层结构.md`:62）：**绝不写消息正文、收件人姓名、邮箱等**；**收件人集合如何算出不入审计**（属实现细节）。
- **交 [#51](https://github.com/NongyuSystem/nongyu-backend-plus/issues/51) 的项**：有界队列容量、后台 flush 周期、批量大小、`publish_revision` 的具体生成规则、「是否要给长尾点赞加时间窗合并」。

## 本票未裁定 / 留 fog

- **`publish_revision` 的生成规则**（公告编辑重发时如何递增）→ #51 或公告域 Spec。
- **有界队列容量 / flush 周期 / 批量大小** → #51（数值）。
- **公告 fan-out 到数万收件人的分批写入策略**（与 #55 Q1 记录的规模代价相关）→ #51。
- **「评论被回复」在无嵌套模型下的收件人边界**（留言作者 vs 帖主可能不同）→ 本票 Q4 的 `source_object_id` 已能区分，但**收件人到底取留言作者还是帖主**需在 Spec 明确（本票倾向取**被回复那条留言的作者**）。
- **通知偏好 / 免打扰**：本期不做。
- **时间窗合并**：本期不做。

## 对下游票的约束
