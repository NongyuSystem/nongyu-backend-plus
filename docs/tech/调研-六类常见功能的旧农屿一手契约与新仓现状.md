> 性质：wayfinder「画地图」前的**第一手事实底稿**，不是实现方案。
> 范围：维护者提出要在新后端做的六类功能——①B 端管理 ②日志埋点 ③文件存储（MinIO）④帖子 ⑤公告 ⑥通知（或内部信）。
> 方法：只读两仓的一手材料（PRD / Spec / 接口文档 / 源码 / 表结构定义 / ADR），逐条回指来源；二手转述不作结论。

> 关键前提：本仓 `README.md:3` 声明「独立于旧农屿 monorepo 的全新仓库，不复用旧后端代码、表结构与部署链路」；因此下文旧仓契约只作**产品语义与 HTTP 契约的历史对照**，不构成新仓的现行约束。[来源: README.md:3]

## 一、B 端管理（Web 管理端 / 管理台）

### 旧农屿一手事实

- 管理端是独立前端应用 `apps/nongyu-web-admin`，用「**教务网学号 + 农屿管理员密码**」登录，管理员密码与教务网密码不是同一套。[来源: ../../docs/nongyu-web-admin/specs/登录与管理端壳.md:16,71,78]
- 登录对接 `POST /api/admin/auth/login`、`GET /api/admin/auth/me`、`POST /api/admin/auth/logout`；统一响应包是 `{ code, message, data }`，`code===0` 为成功（与 Track 埋点服务的 `{ ok, data }` 刻意不同）。[来源: ../../docs/nongyu-web-admin/specs/登录与管理端壳.md:25,190-199]
- 会话存 `localStorage` 的 `nongyu-admin:v1:session`，含 `{ token, user: { id, studentNo, name, role } }`，`role` 必须为 `1` 才视为有效会话；禁止存密码；运行中任一 `/api/admin/*` 返回 401 即清会话跳登录。[来源: ../../docs/nongyu-web-admin/specs/登录与管理端壳.md:112-119,130-132]
- 权限是 `role` 三档：`0` 普通 / `1` 管理员 / `2` 超级管理员；管理员与学生**同表** `users`，管理员密码哈希列 `admin_password_hash` 对普通用户必须为 NULL；`role=1` 时才允许设置/校验该哈希，管理端可多端同时登录。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:109-110,134]
- 有 bootstrap 超级管理员：学号 `202308596` 在业务表无记录时也能登录且**不反填 `users`**；**Admin JWT 不设 `exp`（永不过期）**，仍校验签名、`typ`、角色与账号禁用。[来源: ../../docs/nongyu-node-server/specs/App与Admin鉴权会话策略.md:24-26]
- 管理端业务模块（一手 Spec）：「用户管理」只做查人、看详情、改 `role`、设/重置管理员密码（≥8 位），明确「不改后端契约」「不实现发帖、反馈、建议」，去掉禁用/启用 UI 入口。[来源: ../../docs/nongyu-web-admin/specs/用户管理.md:17,25-29,33-43]
- 「内容管理」侧栏 Tab 为 **公告 / 反馈 / 建议**，对接 `/api/admin/posts*`；公告可列表（含阅读量、覆盖率）、发布、编辑、软删；反馈（`feedback`）与建议（`courtyard`）只列表、详情、软删，「不代发、不编辑正文」；明确「不做富文本编辑器 / 图片上传」，公告内容按纯文本提交。[来源: ../../docs/nongyu-web-admin/specs/内容管理与智慧助手预留.md:24-27,37]
- 管理端对帖子/留言**实名**展示作者（学号 + 姓名），而 App 侧对用户彼此匿名。[来源: ../../docs/nongyu-node-server/specs/广场回复与留言.md:37；../../docs/nongyu-node-server/数据库设计文档.md:171,197-200]

### 新仓现状

- 新仓 `internal/` 下**没有任何管理端业务域**；只有 `identity/`、`school/` 业务域与 `app/`（装配层）、`config/`、`server/`、`platform/`。[来源: internal/ 目录清单；README.md:24-29]
- 但身份域已把「管理台」作为**会话 scope** 与**权限三档**落地：`SessionScope` 有 `app` / `admin` 两套；`platform.Role` 定义 `0/1/2` 三档，注释「沿用旧农屿语义」。[来源: internal/platform/store.go:610-617,723-729；docs/adr/0002-身份仓数据边界.md:67-71]
- 新仓权限判定比旧仓更严：**role 以数据库为准**，令牌里的 role 只作提示；判定兜底必须 **fail-closed**（无法判定一律拒绝）；区分「查不到（按无权）」与「基础设施故障（向上抛错）」。[来源: docs/adr/0002-身份仓数据边界.md:71-74；docs/tech/领域模型-用户与登录-消息.md:140-144]
- 会话模型要求「管理台复用同一套农屿账密登录，但会话独立且必须可吊销、有明确过期」，并点名「旧系统管理票永不过期，这是要修掉的洞」——与旧仓 Admin JWT 永不过期**方向相反**。[来源: GLOSSARY.md:70；docs/tech/领域模型-用户与登录-消息.md:148-150,162]
- 请求层还有一层旧仓没有的约束：**NY1 请求签名**（证明请求来自持有当前密钥的客户端），登录、发验证码、业务接口都要签，仅 `/healthz` 与 `/status` 豁免；且明确**不加 JWT**。[来源: docs/adr/0003-安卓请求签名.md:14-16]
- **effort 边界**：现行 PRD 的范围「**不包含**……Web 管理端」。[来源: docs/specs/prd-学生校外访问学校服务.md:49-51]

## 二、日志埋点

### 旧农屿一手事实：埋点是独立服务，不在业务库

- 埋点数据**不在业务 MySQL 建模**，「由独立服务 `nongyu-go-track-server`（Go + SQLite）承担」；业务库 DDL 明确「不含埋点原始/聚合表（归 Track）」。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:22,38,55,482]
- 分工：**App 直连 Track 上报；管理端经 Node BFF 携带内部 Token 查询 Track**；Track 的 HTTP 契约自称「**本文为 Track HTTP 契约真相；实现须 100% 对齐**」。[来源: ../../docs/nongyu-go-track-server/接口文档.md:7,15]
- Track 与业务 API **刻意不同包**：Track 用 `{ ok, data }` / `{ ok:false, error }`、字段 **snake_case**；Node 业务 API 用 `{ code, message, data }`、camelCase；BFF 代理时应自行映射，**禁止**要求 Track 改成 Node 包格式。[来源: ../../docs/nongyu-go-track-server/接口文档.md:30,41,44-64]
- 契约要点：API 前缀 `/v1`、探活 `GET /health` 无鉴权；App 接口用 `Authorization: Bearer <App JWT>`，与 Node 同一 `JWT_SECRET`，服务端写入的 `user_id` **一律取自 JWT `uid`、忽略客户端伪造**；Admin/运维用 `X-Internal-Token`（常量时间比较）；Body 上限 **1MB**、单用户约 **120 req/min**。[来源: ../../docs/nongyu-go-track-server/接口文档.md:38-42,98-116,122-130]
- 核心端点：`POST /v1/track/events` 批量上报（`events` 1～100 条，`event_id` 为幂等键，重复计入 `duplicated` 不算失败，单条失败计入 `rejected` 走部分成功，队列满返回 503 `QUEUE_FULL`）；`POST /v1/track/presence/offline` 显式离线（**必须**回调 Node 置 `users.is_online=0`）；`POST /v1/internal/events` 供 Node 内部写 `llm_proxy_fail`（**不更新 presence、不回写在线态**）。[来源: ../../docs/nongyu-go-track-server/接口文档.md:189,219-241,272-289,293-329]
- 事件类型枚举 7 种：`screen_view` / `button_click` / `perf` / `app_open` / `heartbeat` / `crash` / `llm_proxy_fail`（后者仅服务端/内部写入）。[来源: ../../docs/nongyu-go-track-server/接口文档.md:132-144]
- Admin 侧端点：`/v1/admin/overview`、`/v1/admin/metrics/trend`、`/v1/admin/metrics/dims`、`/v1/admin/crashes`、`/v1/admin/llm-proxy-fails`、`/v1/admin/jobs/aggregate`、`/v1/admin/jobs/purge`（默认保留 **30 天**）；DAU 口径锁定为「当日存在至少 1 条 `app_open` 且 `user_id IS NOT NULL` 的去重用户数」。[来源: ../../docs/nongyu-go-track-server/接口文档.md:339-400,452-548,378]
- **脱敏**：`props` 序列化后硬上限 **4KB**、超长截断；崩溃列表 `props` 注释「建议含 message / stack 等，**禁止明文密码**」；客户端对接要点第 5 条「`props` 禁止明文密码」。[来源: ../../docs/nongyu-go-track-server/接口文档.md:230,479,616]
- 共享契约包 `packages/nongyu-track-contract`：`TRACK_EVENT_TYPES` 为 App SDK 允许的 6 种（不含 `llm_proxy_fail`）；`TRACK_SERVER_EVENT_TYPES` = 前 6 种 + `llm_proxy_fail`；`TRACK_PLATFORMS = ios/android/web`；`TRACK_WEB_INGEST_ALLOWLIST` 为官网 Web ingest 允许的 6 组 `(event_type, event_name)`（5 个 CWV + `screen_view/web_home`）；`TrackEvent` 字段为 snake_case（`event_id / event_type / event_name / client_ts_ms / session_id / app_version / props` 等）。[来源: ../../packages/nongyu-track-contract/src/index.ts:2-9,13-24,35-46,63-65]
- **现状**：Go 版埋点服务已下线（「生产 CD 不再发布」），现行实现是 `apps/nongyu-node-track-server`（Fastify + better-sqlite3），Go 目录「仓库保留、不删除」，「禁止把本目录当作现行源码修改」。[来源: ../../apps/nongyu-go-track-server/DEPRECATED.md:1-7]

### 新仓现状

- 现行 PRD 的范围「**不包含**……埋点服务」；本仓 README 明确 `apps/nongyu-go-track-server` 是「旧农屿已下线的 Go 埋点服务，仅作历史对照，**不是本仓库的现行源码或依赖来源**」。[来源: docs/specs/prd-学生校外访问学校服务.md:49-51；README.md:84]
- `internal/platform` 接口清单里**没有任何埋点/事件上报接缝**（14 个 interface 全见「新仓约束清单」一节）；`internal/` 全目录 grep `TRACK|埋点|Event` 无业务命中。[来源: internal/platform/ 各文件；见「新仓约束清单」]
- 新仓现行「可观测性」是**日志 + 审计**两条，不是埋点：运行日志只写 stdout/slog，由外部采集器（尚未部署）送 ES；审计走 `PGAuditStore` 落 Postgres `audit_log`。[来源: docs/tech/持久层结构.md:13-18,109]

## 三、文件存储（MinIO）

### 旧农屿一手事实

- **决议原文在 PRD**：图片存储「走**自建 MinIO（S3 兼容）**，Node 通过 S3 SDK 读写；对象 key 形如 `posts/{yyyy}/{MM}/{uuid}.{ext}`」；澄清结论（grill）表写「**自建 MinIO（S3 兼容）**，不引入阿里云 OSS、不做本地磁盘方案」；非目标重申「不做图片 CDN、不做阿里云 OSS」。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:47,81,99]
- 契约细节：反馈墙与大院帖都可带图，**最多 9 张**；单张服务端硬限 **5MB**，前端上传前压缩（最长边 2560px、JPEG q0.8）；允许 `jpg/png/webp/gif`；发布时只提交**已上传成功的对象 key**，草稿里也只存对象 key、不存本地临时文件路径；`images` 校验要求「每项必须是本桶前缀下的合法 key（防外部 URL 注入）」。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:40,43-49,63]
- 背景自述：一期「**完全没有图片通道**：Node 无 multer / S3 / 静态目录，`express.json limit 2mb` 也不支持 multipart；`posts` 表无图片字段」。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:19]
- 另一条独立的一手记录（皮肤/资源包 effort）印证存储层选型：「**存储层已定 MinIO（S3 兼容）**……已拍板待带入：后端单起 Go、只做资源防盗链/预签名 URL 不需要 SSO、色值走数据库下发」；并明确「MinIO 不提供身份认证」「预签名 URL 是 bearer token，不做身份认证/SSO，也不做内容完整性校验」。[来源: ../../apps/nongyu-app-plus/docs/research/skin-decoupling-routes.md:5,22,254；../../apps/nongyu-app-plus/docs/adr/0002-主题token层用自建CompositionLocal承载.md:39]
- 该笔记同时自列未验证项：「**MinIO 官方 presigned URL 文档 404**，本轮以 AWS S3 官方文档作 S3 语义的一手依据，**MinIO 具体 API 名/行为未验证**」。[来源: ../../apps/nongyu-app-plus/docs/research/skin-decoupling-routes.md:358]

### 新仓现状

- `internal/platform` **没有对象存储接缝**：14 个接口里无 `ObjectStore` / `BlobStore` / `S3` 类抽象；`internal/` 全目录 grep `MinIO|minio|S3|对象存储` 无命中。[来源: internal/platform/ 各文件；见「新仓约束清单」]
- 架构上明确禁止业务域直接引用具体实现：README 第 2 条「业务域只依赖 `internal/platform` 定义的接口，**不直接 import 数据库驱动、S3 SDK 等具体实现**」；第 3 条「**进程无状态**：状态全部外置（DB / 缓存 / **对象存储**），以便水平扩副本」——即对象存储是**被允许的外置位置**，但接缝须先在 `platform` 定义。[来源: README.md:45-46]
- 现行 PRD 的范围「不包含……内容、广场」，也未列文件存储。[来源: docs/specs/prd-学生校外访问学校服务.md:49-51]

## 四、帖子

### 旧农屿一手事实

- 统一 `posts` 表 + `post_type` 三值承载三类内容：`announcement`（农屿公告，管理员，只读）/ `feedback`（反馈墙，用户，App 展示匿名）/ `courtyard`（农屿大院，用户，App 展示匿名）。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:15；../../docs/nongyu-node-server/数据库设计文档.md:161-171]
- 表字段：`subtype` VARCHAR(32)、`title` VARCHAR(200)、`content` MEDIUMTEXT、`author_user_id`、`view_count`、`unique_reader_count`、`deleted_at`（软删）、`published_at`（列表默认倒序）、`created_at/updated_at`；索引 `(post_type, published_at)`、`(author_user_id, published_at)`、`(deleted_at, published_at)`。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:173-187,373-394]
- 阅读统计用独立 `post_reads` 表，唯一约束 `(post_id, user_id)`：首次插入 `view_count++` 且 `unique_reader_count++`，重复打开只 `view_count++`；覆盖率 = `unique_reader_count / 总用户数`。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:228-238,271]
- **App 侧匿名**：列表/详情不下发作者姓名/学号/userId；管理端接口可查 `authorName` / `authorStudentNo`。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:171]
- HTTP 契约：`POST /api/app/posts` 请求体 `{ postType: feedback|courtyard, subtype, title(1-200), content }`；`feedback` 帖在配置 `GITHUB_TOKEN`+`GITHUB_REPO` 时**异步**建 GitHub Issue（best-effort，失败只记日志、不回滚帖子）；`GET /api/app/posts/:id` 成功打开即计阅读且不返回阅读量；`DELETE /api/app/posts/:id` 作者软删自己的帖，公告不可删；`GET /api/app/users/me/posts` 查「我的帖子」（不含公告，此项展示 `viewCount`）。[来源: ../../docs/nongyu-node-server/接口文档概览.md:432-440,460-486,473-480]
- 一期 App Spec 边界：三区分段、纯文本发帖、公告只读、首页通知栏、我的帖子；「**不做评论、点赞、图片/音频、HTML 富文本**」「**不支持用户编辑已发布帖子**」「App 列表/详情**永不展示** viewCount/uniqueReaderCount」。[来源: ../../docs/nongyu-rn-app/specs/广场功能.md:29-34,38-45]
- 后续 PRD（发帖增强）才把图片、编辑、校验补上：发布后 **24 小时内**作者可编辑本人帖的标题/正文/subtype/图片、次数不限，**公告不可编辑**，编辑窗口以**服务端判定** `canEdit` 为准，详情/列表展示「已编辑」标记 `editedAt`；后端补 `subtype` 按 `postType` 分桶白名单、`content` 上限 5000、按用户维度发帖/编辑频率限制、回参补 `images`/`editedAt`/`canEdit`；反馈墙编辑后同步更新 GitHub Issue（失败只记日志）。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:51-65,53-57]
- 该 PRD 明确「不回退匿名性：反馈墙与大院对用户彼此匿名，`authorDisplayName` 恒为 null；署名仅管理端可见」「不做 push 通知（沿用现有前台轮询）」。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场发帖增强PRD.md:102-104]

### 新仓现状

- 无帖子业务域、无 `posts` 表、无相关 PRD/Spec；`migrations/` 下只有审计表（0001）、身份域四表（0002）、学工档案四表（0004）等，`platform` 的 `Store` 接口骨架期只有 `Get(ctx,key)` 一个方法。[来源: internal/platform/store.go:23-30；docs/tech/持久层结构.md:110；README.md:7,17]
- 现行 PRD 范围「不包含……内容、广场」。[来源: docs/specs/prd-学生校外访问学校服务.md:49-51]
- 若将来要做，`持久层结构.md` 已把「用户偏好、提醒规则等」将来的业务表归 **Postgres**（结构化真相层），且本仓用 Postgres + pgx 而非旧仓 MySQL + mysql2。[来源: docs/tech/持久层结构.md:9；internal/platform/store.go:16-18]

## 五、公告

### 旧农屿一手事实

- 公告不是独立表/模块，而是 `posts.post_type='announcement'` 的一个取值，作者为管理员、客户端只读。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:163-169；../../docs/nongyu-rn-app/specs/广场功能.md:31]
- HTTP 契约：`GET /api/app/posts/announcements/latest` 返回 `{ id, title, subtype, publishedAt } | null`，供 App **首页通知栏**使用，点击直达公告详情；公告墙**不参与**列表 30s 轮询（由用户自行下拉刷新）。[来源: ../../docs/nongyu-node-server/接口文档概览.md:427-430；../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场回复与留言PRD.md:49-51]

## 六、通知（或内部信）

### 旧农屿一手事实：没有独立消息中心，只有「帖子派生通知」

- 新仓领域模型的一手对照行写得很直白：旧农屿「**消息中心｜不存在（帖子派生通知）**」；更正记录补充「旧农屿里也没有独立消息域」。[来源: docs/tech/领域模型-用户与登录-消息.md:8,163]
- 通知形态是**前台轮询 + toast**，不是推送：用户在前台以 **30s** 为间隔轮询「自己的帖子是否被回复」，有新回复则 toast；列表轮询仅在广场 Tab 前台，「自己帖子被回复」轮询在 App 任意前台页面；**不做推送通知**、**不做后台轮询**。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场回复与留言PRD.md:46-52,64,74-75]
- 「新的回复」由**服务端**判定：「为每条回复/留言维护针对帖子作者的**『是否已通知』标记，通知后置位**，避免重复 toast」。[来源: ../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场回复与留言PRD.md:52,65]

#### `notified_author` 的语义（重点核查项）

- 字段定义在 `post_replies` 表：`notified_author TINYINT(1) NOT NULL DEFAULT 0`，「是否已通知帖子作者（0=待通知，轮询后置 1）」；索引 `idx_replies_notified (notified_author, post_id)`；`PATCH admin_reply` **不重置** `notified_author`（已通知过的作者不因编辑再次被提醒）。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:193-224,209,217,224,420,427]
- Spec §4.3 完整语义：新建 `admin_reply` / `comment` 时置 0；**仅当回复的 `post.author_user_id` 为当前轮询用户时**，该回复才进入「我的新回复」通知流；轮询接口返回这些 `notified_author=0` 的回复后**同事务内置位为 1**，每条只触发一次 toast；帖子被软删后其下回复不再进入通知流。[来源: ../../docs/nongyu-node-server/specs/广场回复与留言.md:77-82,143-149]
- 源码印证：`consumeNewRepliesForUser` 用 `SELECT ... JOIN posts ... WHERE p.author_user_id = ? AND r.notified_author = 0 ... ORDER BY r.created_at ASC LIMIT 50 FOR UPDATE`，随后 `UPDATE post_replies SET notified_author = 1 WHERE notified_author = 0 AND id IN (...)`；`FOR UPDATE` 是为串行化并发轮询、避免重复 toast。[来源: ../../apps/nongyu-node-server/src/modules/posts/postReplies.repo.ts:325-353]
- **结论：不是 per-user 已读状态**。它是**每条回复/留言行上的一个布尔位**，语义是「这条回复是否已经给『帖主』推过一次 toast」；一个帖子只有一个作者（`posts.author_user_id`），因此不存在多收件人、也不存在「每用户一行已读」的表。置位动作发生在**回复行**上，不是独立的 `notification_read` 关系表；通知流的过滤条件是「我是这个帖子的作者」。[来源: ../../docs/nongyu-node-server/specs/广场回复与留言.md:80-81,143-144；../../apps/nongyu-node-server/src/modules/posts/postReplies.repo.ts:334-352]
- 相关但不同的两个端点：`GET /api/app/users/me/post-replies/new`（**轮询用**，有副作用：返回项的 `notified_author` 置 1，后续不再返回，单次最多 50 条）；`GET /api/app/users/me/post-replies/received`（**收到的回复 inbox**，帖主视角，排除自己留在自己帖下的，分页）——后者是查询视图，不改通知位。[来源: ../../docs/nongyu-node-server/接口文档概览.md:488-503；../../apps/nongyu-node-server/src/modules/posts/routes.ts:300-321,344-354]
- 回复/留言本体：`post_replies` 用 `kind` 区分 `admin_reply`（反馈墙管理员单条回复，1:1，所有用户可见但管理员身份匿名化，增删改不留痕）与 `comment`（大院用户顶层留言，1:N，用户间完全匿名仅 `isMine` 自识，可删不可编辑）；`admin_reply` ≤2000 字、`comment` ≤1000 字；不做嵌套回复（无 `parent_reply_id`）。[来源: ../../docs/nongyu-node-server/数据库设计文档.md:193-224；../../docs/forhuman/rawprds/nongyu-rn-app/Center/广场回复与留言PRD.md:18-30；../../docs/nongyu-node-server/specs/广场回复与留言.md:29-35,99-135]

## 新仓约束清单（跨六功能，长期不可破）

### A. 架构与流程

1. **模块化单体**：一个仓库 / 一个 module / 一个进程，内部按业务能力强分包；业务域之间不互相 import，协作统一走 `internal/app` 装配层编排。[来源: README.md:15,44]
2. **业务域只依赖 `internal/platform` 接口**，不得直接 import 数据库驱动、S3 SDK 等具体实现；「新增能力时在此扩展方法，不要另起一套平行接口」。[来源: README.md:45,47；internal/platform/store.go:23-26]
3. **进程无状态**：状态全部外置（DB / 缓存 / 对象存储），以便水平扩副本。[来源: README.md:46]
4. **SDD 流程**：PRD → Spec → 技术方案（按需）→ 实施计划 → 编码 → 人工 Review；「**业务接口开发前须先补 PRD 与 `docs/specs/` 下的规格，禁止无规格直接写业务代码**」。六类功能目前**都没有**新仓 PRD/Spec。[来源: README.md:77-80]
5. **不复用旧后端代码 / 表结构 / 部署链路**；旧 `nongyu-go-track-server` 仅作历史对照，不是现行源码或依赖来源。[来源: README.md:3,84]
6. 请求层有 **NY1 请求签名**（HMAC-SHA256，±5 分钟窗、nonce 一次性、密钥可轮换可吊销），登录/发验证码/业务接口都要签，`/healthz` 与 `/status` 豁免；明确**不加 JWT**。[来源: docs/adr/0003-安卓请求签名.md:14-17]

### C. 持久层分工与「应用不直连 ES」

- 三层分工：**Postgres 18**（独立库 `nongyu`）放结构化真相（审计流水 `audit_log`、将来业务表），**不放**票据/缓存/日志原文；**Elasticsearch 9.1.4 + Kibana** 放运行日志的检索与可视化，**不放**业务真相；**Redis 8.10** 放票据、缓存、幂等锁、限流计数、状态上报，**不放**需长期留存的审计数据。[来源: docs/tech/持久层结构.md:5-11]
- **应用不直连 ES**（#24 决策，2026-11-09）：运行日志只写 stdout/slog，由外部采集器（Filebeat / Vector / Fluent Bit，**尚未部署**）送进 ES；「代码里没有任何 ES 依赖是符合本设计的，不是遗漏」；理由是把日志当可丢的旁路数据，避免 PG/ES 双写把一致性引入业务代码。[来源: docs/tech/持久层结构.md:13-18,22-26,109]
- Spec 亦记录「Elasticsearch 完全未接；没有 metrics/tracing」「M8 Elasticsearch 未接入」「ES 的日志写入与检索实现（当前审计落 Postgres；若后续接入，另立规格）」「ES 是否真的需要——待定」。[来源: docs/specs/spec-身份域与平台底座.md:29,159,171,194]
- 票据**不进 PG**（短期凭据、高频读写、原子过期语义，Redis 更合适）；票据是持久数据不能丢，与「可再生、可丢」的通用缓存刻意分开。[来源: docs/tech/持久层结构.md:28-30；docs/tech/Redis基础能力与边界.md:5-14]

### D. 日志 / 审计 / 埋点三者的现行边界

| | 载体 | 内容 | 硬约束 |
| --- | --- | --- | --- |
| **运行日志** | stdout / slog → 采集器 → ES（应用不直连） | 运行日志、结构化字段 `userID/action/result/target` | 不写票据/密文；采集器未部署 [来源: docs/tech/持久层结构.md:13-18,109；docs/tech/回传端点契约-现有能力底座.md:110] |
| **审计** | `PGAuditStore` → Postgres `audit_log` | `request_id / user_id / action / target / result / occurred_at`，只有标识性字段 | **旁路**：异步批写、满缓冲丢弃并计数，「宁可丢审计，也不能因为审计库慢让用户登录失败」 [来源: docs/tech/持久层结构.md:36-43,48-60] |
| **埋点** | 新仓**没有**；旧仓是独立服务 | 旧仓事件上报/DAU/崩溃/性能 | 现行 PRD 明确「不包含埋点服务」；旧服务非本仓依赖来源 [来源: docs/specs/prd-学生校外访问学校服务.md:51；README.md:84] |

- **审计表铁律**：「表里只有标识性字段。**绝不写票据、密文、验证码、上游响应体**——审计表不能成为泄漏面」；`AuditEntry` 结构体注释同义（「只允许放标识性字段。绝不添加票据、密文、验证码、上游响应体等字段」）。[来源: docs/tech/持久层结构.md:62；internal/platform/mail.go:396-399]
- 审计流水号由 `server.RequestIDMiddleware` 生成（优先复用调用方 `X-Request-Id`），写入 context 与响应头，使「一次请求的多个动作可以在表里串起来」。[来源: docs/tech/持久层结构.md:50,64]
- 限流与审计按可见范围分段：凡经后端的交互（换票、票据续期/失效判定、代请求）**必须**记审计（谁、何时、目标逻辑名、结果码）并按用户分级限流；**客户端直连学校的只读请求后端既无限流也无审计**，是被显式接受的盲区，不得声称「所有请求均已限流」。[来源: docs/adr/0001-服务端代请求边界由新后端重写.md:28,43]

- **身份证号**：ADR-0002「**日志 / 审计 / 埋点 / 错误信息永不出现身份证号**」，完整号 AES 加密落 `user_profiles.id_card_sealed`、允许接口返回但须逐接口显式授权，且密码镜像与身份证用**两把独立密钥**。[来源: docs/adr/0002-身份仓数据边界.md:28-45,104-111]

- **画像字段分权**（顺带影响 B 端管理）：学校档案字段（姓名、学院、专业、班级、年级、身份证号、姓名拼音首字母）**只允许服务端在学校认证/教务抓取成功后写入**；农屿扩展（QQ、头像、偏好）只允许本人修改；「客户端提交的画像字段**一律不得覆盖学校档案字段**」——直接针对旧农屿「登录时请求体整体覆盖画像」的安全洞。[来源: docs/adr/0002-身份仓数据边界.md:76-83,13]
