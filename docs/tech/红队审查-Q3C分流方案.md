## 结论摘要

**这个方案在当前的文字表述下不成立，卡在两处相互咬合的自相矛盾上，且第二处是我这次审查新发现、此前底稿未记录的一条硬事实。**

第一，**「票据本体不出后端」与「客户端直连学校」不可同时成立**。学校侧唯一认得的凭证就是 `webvpn.sicau.edu.cn` 上 HttpOnly 的 `wengine_vpn_ticketwebvpn_sicau_edu_cn`，网关按这张票在服务端补上游 Cookie（[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:179]；[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:300]）。客户端若要直连，票就必须到客户端；票一旦到客户端，「不出后端」就破产。而「一次性访问许可」这个东西学校**根本不认**——它是农屿自己签的凭据，网关没有任何机制去验证它。所以 C 方案的「许可 + 编码后地址」下发，实质等于「票必须随之下发」，「许可」这一层是纯装饰。

第二（新发现，也是最致命的一条）**「票放在客户端、客户端直连」这条路连旧仓都没走通，而且不是「未测」，是旧仓自己写下的失败前提**。二次复核发现一个结构性事实：客户端直连（不经后端）时，网关若因票死返回 `302 → https://webvpn.sicau.edu.cn/login`，**这个 Location 指向 webvpn 域、而不是真站**，而旧客户端只在 `Location` 指向真站时才再编码（[来源: @OLD/docs/nongyu-rn-app/specs/WebVPN传输适配.md:30]；[来源: @OLD/packages/nongyu-tool-jiaowu/core/webvpn/encode.ts:126]），因此「票死 → 302 → /login」在客户端会**自动变成一次对学校登录页的 GET**，客户端自己拿不到可判别的信号。更关键的是，旧 App 的**直连模式根本没有在校外可用的登录入口**：`probeDirectJiaowu` 探不到教务时 `prepareJiaowuTransport` 返回 `webvpn`，登录页随即走门户换票（[来源: @OLD/apps/nongyu-rn-app/src/modules/jiaowu/components/JiaowuLoginForm.tsx:84-93]；[来源: @OLD/packages/nongyu-tool-jiaowu/core/login/cas.ts:705-713]），而这条门户换票链**本身就要先能拿到有效票**——也就是说旧仓里「票从哪来」这件事从来没有离开过「客户端自己走完双 CAS」这条路径，从来没有「后端发许可 / 发地址」这一步。C 方案假设客户端能在没有票的情况下启动，这一步在仓内**没有任何先例支撑**。

综合：C 方案若照字面实现（票不出后端），客户端无法被学校识别；若补上「票要下发」，它就退化成方案 A（票在客户端），而方案 A 的旧实现已经被底稿记录为「完整链路未用真账号验收」（[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:217]）。此外 C 方案赖以立身的「把压力推给客户端就不会撞学校频率限制」这一条，一手材料**只字未提**限制是按账号还是按 IP，反而有「WebVPN 出口 IP 可能共享，误伤风险」（[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:328]）——把请求推给客户端**并不必然**降低风险。

## 逐条问题

### 问题 1：「访问许可」到底是什么？学校根本不认它

**问题陈述**：C 方案下发「短时效、绑定单次业务操作、不可重放」的「访问许可 + 编码后地址」，但全文未说许可由谁签发、学校拿它做什么。「不可重放」这个属性只在农屿自己能验证的范围内才有意义——它是农屿签的，网关没有理由也不会校验它。

**一手证据**：

- 客户端请求校内资源时，网关认的只有 `wengine_vpn_ticketwebvpn_sicau_edu_cn`：`Domain=webvpn.sicau.edu.cn`、`HttpOnly`、会话级；「无有效值则 jiaowu 等资源 302 登录」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:179]
- 「网关用 vpn ticket 在服务端补上游 Cookie，客户端不必自己再贴 `ASPSESSIONID*`」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:300]
- 网关侧的唯一身份校验面是 CAS 票据 XML 校验，而不是任何第三方签发的 token：「说明 WebVPN 侧按 **CAS 票据 XML 校验** 升级会话，而不是忽略 ticket（实测 2026-10-30）」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:142]
- 未认证一律拦截：「未认证时访问编码后的教务路径一律 `302 Location: https://webvpn.sicau.edu.cn/login`」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:17]

**推论**：网关只做两件事——按 cookie 里的票认人、按编码路径还原目标。它没有任何插件、握手或扩展点能识别农屿自签的「一次性许可」。仓内**未找到**任何「网关可被第三方 token 授权」的记录。

> 需要公平指出的一点（避免过度指控）：**编码后地址本身就是明文可算的**。`WEBVPN_KEY` 与 `WEBVPN_KEY_HEX` 都是写死的常量，`encodeVpnHost` 是纯函数、无 I/O、无 Cookie、无 `main.js`。[来源: @OLD/packages/nongyu-tool-jiaowu/core/webvpn/encode.ts:11-17]；[来源: @OLD/packages/nongyu-tool-jiaowu/core/webvpn/encode.ts:100-128]；[来源: @NEW/docs/tech/旧农屿WebVPN可重写契约清单.md:275] 所以「下发编码后地址」这一步在安全上**不增加也不需要**任何许可来背书——地址谁都能自己算出来，许可保护的是一个本来就公开的东西。

**严重度：致命**（它使 C 方案与 A 方案在「票是否到客户端」这个关键差异上无法维持，见问题 5）。

### 问题 2：客户端如何「直连学校」？——只要票不出后端，就直连不了

**问题陈述**：C 方案声称执行 HTTP 的是客户端、票不出后端。但客户端要「被学校识别为已登录」，唯一的办法是在 `webvpn.sicau.edu.cn` 上持有有效票。

**一手证据（正面）**：

- 旧客户端带票请求靠的是 Android 原生模块读写 `java.net.CookieHandler`（RN XHR 用的那只罐子，不是 WebView 的 `CookieManager`），常量 `ORIGIN = "https://webvpn.sicau.edu.cn/"`、`TICKET_NAME = "wengine_vpn_ticketwebvpn_sicau_edu_cn"`，导出 `readTicket/writeTicket/clearTicket`。[来源: @OLD/apps/nongyu-rn-app/modules/nongyu-webvpn-cookie/android/src/main/java/expo/modules/nongyuwebvpncookie/NongyuWebVpnCookieModule.kt:15-27]；[来源: @OLD/apps/nongyu-rn-app/modules/nongyu-webvpn-cookie/android/src/main/java/expo/modules/nongyuwebvpncookie/NongyuWebVpnCookieModule.kt:73-76]
- 票据被抄进并写回 SecureStore，供冷启动恢复：`SecureStore.setItemAsync(TICKET_KEY, value)`。[来源: @OLD/apps/nongyu-rn-app/src/modules/jiaowu/auth/webvpnTicket.ts:25-35]；冷启动 `native.writeTicket(value); setJiaowuTransport("webvpn")`。[来源: @OLD/apps/nongyu-rn-app/src/modules/jiaowu/auth/webvpnTicket.ts:41-53]
- 请求侧必须显式打开凭证：「`withCredentials=false` 时 RN 可能不发也不收 cookie，必须显式打开」。[来源: @OLD/packages/nongyu-tool-jiaowu/core/utils/request.ts:44-45]

即在旧仓的既有实现里，「客户端能直连」这件事**成立的前提就是票在客户端**。

**一手证据（反对「客户端直连可自动恢复」）**：

- 旧客户端把「票死」识别为「最终 URL 以 `https://webvpn.sicau.edu.cn/login` 开头」，**并且依赖 axios 自动跟随 302 之后的 `responseURL`**：`const vpnTicketDead = finalUrl.startsWith("https://webvpn.sicau.edu.cn/login")`。[来源: @OLD/packages/nongyu-tool-jiaowu/core/utils/request.ts:206-207]
- 而 `Location` 的重写只针对**上游真站**的绝对地址：规格写「`service` / `callbackUrl` / 302 `Location` 若指向真站，再编码一次」。[来源: @OLD/docs/nongyu-rn-app/specs/WebVPN传输适配.md:30] 编码器对已属 webvpn 域的地址原样返回。[来源: @OLD/packages/nongyu-tool-jiaowu/core/webvpn/encode.ts:126]

于是出现一个**C 方案必须正视的结构性后果**：票死时网关返回的是 webvpn 域自己的 `/login`，客户端「看到 302 → /login」这一步**只能在跟随重定向之后、从最终 URL 反推**，而不是在拿到 302 的那一刻判断。这在客户端直连形态下意味着：每次票死都会真实地打到学校的 `/login` 页一次（403/302 的往返已经发生），并且「未登录」与「登录后又踢回登录页」在响应层面长得很像。

> **诚实标注**：上面这条**不是**从「302 转到 `/login` 就没有凭证泄漏面」这个角度写的——`/login` 是 webvpn 自己的域，凭证自然走不到真站。我要指出的只是：**客户端直连 → 网关拒绝 → 自行跳登录页**这条链，在旧仓里从未被写成「可自动恢复」，而 C 方案把「后端能解决则给新的」当成闭环的一环，这一环在客户端侧**缺少可判别的入口**（详见问题 4）。

**严重度：致命**（与问题 1 合并构成本方案的中心矛盾）。

### 问题 3：「15 秒限制由用户承担」是否真实成立？——仓内无法判断，且方向可疑

**问题陈述**：C 方案的全部经济性论证建立在这一条上：把高频只读请求推给客户端，后端不承压，于是不会触发学校的频率限制。

**一手证据**：

- 关于限制，仓内**只有一句话**，且它说的是「恶意下载拉黑」，来源是登录页须知摘录，**没有说明限制的作用维度（账号 / IP / 会话）**：「须知：账号仅限本人；恶意下载拉黑（1 分钟内间隔 <15s 基础限制；连续 5 次 → 1 小时限制）」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:327]
- 同类风险条目明确提到出口维度的误伤：「与直连相同；WebVPN 出口 IP 可能共享，误伤风险」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:328]
- 登录页须知原文：「**账号仅限本人**；禁止连续、系统、集中、批量下载；触发频率限制会加入黑名单」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:334]
- 本仓底稿已把这条列为「不影响结论但影响方案」的张力点：ADP-0001 第 4 条的直接依据就是「学校 `1 分钟内间隔 <15s` 基础限制、`连续 5 次 → 1 小时`、多账号共享出口 IP 易被误伤」。[来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:28]

**判断**：**仓内未找到**任何证据能确定限制是按账号还是按 IP。

- 若限制**按账号**：C 方案确实把 N 个用户的压力拆成 N 个账号各自的 15 秒间隔，后端不承压这条成立。这是 C 方案唯一可能的立足点。
- 若限制**按 IP**：C 方案把请求推到客户端，而客户端在校园网内共享同一个 NAT 出口，压力**只是从「后端进程的出口 IP」变成「学校网关出口的 IP」**，被拉黑的概率未必下降；更糟的是后端失去对总量的观测，连「有人快要触发限制」都无从得知，而 ADR-0001 第 4 条「按用户分级限流 + 审计」[来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:28] 在 C 方案里**无处落地**——因为请求不再经过后端。

**还有一个会被忽略的点**：「连续、系统、集中、批量下载」被须知明确禁止。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:334] 抢课场景下「每人 15 秒点 3 下」在**行为形态**上恰好是「集中、批量」的客户端特征；把执行方从后端换成客户端，**不改变行为形态**，只改变观测方是谁。所以「后端不承压」是工程收益，不是合规收益——C 方案的表述把两者混在了一起。

**严重度：重要**（不是证伪，而是「该论断没有被一手材料支持，且方向可疑」）。

### 问题 4：客户端判断失败原因不可靠——而且「可区分」的前提条件在客户端不成立

**问题陈述**：C 方案把「校园网不可达 / 票过期」的判定放在客户端，并设计「失败时客户端判断 → 后端能解决则给新的」。问题是这个判定需要的信息，客户端在直连形态下拿不全。

**一手证据**：

- 两种失效有官方定义的判别方式：「302 到 `/login` 表示 ticket 已死；正文是「登录超时」表示 ticket 还在、教务会话已死」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:310]
- 但这两个信号在旧实现里都是**后端/客户端绕开 302 之后**才能拿到的：票死靠「最终 URL 前缀」（需要自动跟随），教务会话死靠**响应正文里含「登录超时」/「账号验证失败」**。[来源: @OLD/packages/nongyu-tool-jiaowu/core/utils/request.ts:206-207]
- 更麻烦的是「教务会话死」这一种，判定依据是**中文正文子串**，而响应体是 GBK、需要手动解码（`responseType: "arraybuffer"`，注释「默认返回 arraybuffer 以便手动解码 GBK」）。[来源: @OLD/packages/nongyu-tool-jiaowu/core/utils/request.ts:42] 客户端做这件事本身可以（旧仓就在做），但如果「票不出后端」，那么票是否活的判断**必须由后端替客户端做**——而后端已经不打这个请求了，它没有任何输入可以判断。这在逻辑上直接闭死：**「后端判断票是否过期」依赖「后端发出请求」，而 C 方案把请求移出后端。**
- 另一端，「校园网不可达」的判定已有既定做法与固定文案：`probeDirectJiaowu` 4 秒超时、任何 HTTP 响应即 `true`。[来源: @OLD/packages/nongyu-tool-jiaowu/core/login/cas.ts:690-703]；超时统一映射为「教务网迁入内网，可尝试连接校园网使用农屿」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN可重写契约清单.md:213]

**判断**：「校园网不可达」客户端**可以**判定（旧仓已成体系）；「票过期」与「教务会话死」客户端**拿不到判定所需的权威信号**，除非票就在客户端手里（即退化成 A）。C 方案的「客户端判断」在这一半上是**莫须有的策略**——它假设了一个客户端并不拥有的判断能力。

**附带一个真实存在但被低估的工程坑**：旧客户端对**所有**网络错误最多重试 3 次、每次延迟 1 秒、且重试前不区分错误类型：`if (config && (config._retryCount || 0) < 3) { ... setTimeout(1000) ... return service(config) }`。[来源: @OLD/packages/nongyu-tool-jiaowu/core/utils/request.ts:219-227，行号为该段落范围] 这与「15 秒间隔」直接打架——一次失败在 3 秒内打出 4 个请求，本身就是最容易触发 <15s 限制的形态。若 C 方案把重试逻辑留在客户端，就必须同步定义「重试也要计入 15 秒」，否则「15 秒由用户承担」这句自相矛盾。

**严重度：重要**。

### 问题 5：设计过度——若不成立，则「访问许可」这一层纯属多余；若不退让，则回到 A

**问题陈述**：这是一个二难。C 方案在一句话里同时断言了两件事：

（a）票不出后端；
（b）客户端执行 HTTP，且下发「一次性访问许可 + 编码后地址」。

若能同时满足 (a)(b)，则「许可」是多余抽象——因为
- 地址可自行计算（常量 + 纯函数），见问题 1 的公平说明；
- 请求的鉴权完全交给学校网关，许可不能替代票；
- 一次性 / 不可重放这两个属性，只有农屿自己能校验，而请求根本不经过农屿。

也就是说，「许可」既不参与鉴权、也不保护机密信息、也不控制幂等（幂等应该由业务层管），它在功能上是**零**。这是典型的设计过度：为「不理解的问题」（担心客户端滥用地址）引入了一个**无法生效**的机制。

若 (a) 不能成立（见问题 1、2），则票必须下发到客户端，C 方案退化为**方案 A 的近似**，唯一的区别是「谁来决定地址」——而这恰恰是最不重要的一点。

**另有一条更朴素的反向论证**：既然能让票到客户端（方案 A 的形态），那么后端从一开始就不必存在「编码后地址下发」这一步，客户端自己就有编码器（旧仓 `encode.ts` 是客户端包）。C 方案在后端重写这套能力，同时又要让客户端执行——这等于**把已经能跑在客户端的能力挪到后端，再把它发回客户端**，中间多出一跳网络与一套状态（问题 6 的「校内/校外上报」）。ADR-0001 的出发点本来就是「后端是否代请求」，而不是「地址由谁计算」。

**严重度：重要**。这一条不是"错"，而是"多"——如果维护者的真实意图是"降低后端压力"，那么正确的表述应该是"高频只读走客户端直连（票在客户端）"，而不是给这条路配一套自签许可。

### 问题 6：与 ADR-0001 的一致性——第 3 条部分成立，第 5 条单向成立；但 ADR 第 4 条在 C 方案下无处落地

C 方案声称保住 ADR 第 3 条（票不出后端）与第 5 条（不回显 Set-Cookie）。逐条核对：

| ADR 条目 | 原文 | C 方案是否成立 | 一手依据 |
| --- | --- | --- | --- |
| 第 1 条：目标集合固定白名单、调用方不传 URL | 仅三域，调用方只传逻辑目标名 | **C 方案削弱了这一条**：若地址由后端下发而客户端自行请求，则进入「客户端可以请求任意编码 URL」的形态；仓内未找到 C 方案对客户端目标集合的任何约束。而 SSRF 风险条目禁的正是「接受用户传入并请求任意 WebVPN 编码 URL」。[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:329] | [来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:25] |
| 第 2 条：每请求归属已认证用户 | 代请求必须归属到具体学生 | **在 C 下失效或错位**：执行请求的不再是后端，归属只能靠客户端自报；后端对「谁真的打了这一下」无审计。 | [来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:26] |
| 第 3 条：票据加密外置、不入日志 | `wengine_vpn_ticket*` 加密外置到 Store | **字面成立，实质存疑**。C 说票不出后端，则票留在后端存储——但客户端要直连就需要票（问题 2 已证），两者无法同时成立。若「许可」是票的替代品，则第 3 条形式上未破，但第 3 条的**目的**（票外置以便后端代请求）已经落空：后端不再代请求，票的存在理由只剩「换票生命周期」。 | [来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:27] |
| 第 4 条：按用户分级限流 + 审计 | 主体仍是用户侧发起、按用户分级限流、每次代请求记审计 | **彻底落空**：请求不经后端，无分级限流、无审计。这是 C 方案与 ADR **最尖锐的冲突**，而 C 方案的自述里完全没提。 | [来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:28] |
| 第 5 条：不跟随真站、不回显 Set-Cookie | 302 只在 webvpn 域跟随；上游 Set-Cookie 不回显 | **一半成立，一半不再适用**。「不回显 Set-Cookie」在 C 下自动成立（后端不做请求）；但「302 只在 webvpn 域内跟随」的**控制方**从后端挪到了客户端，后端对此**没有强制点**——客户端跟不跟真站，后端管不到。另外「票据失效与教务会话失效映射为两个可区分错误码」这条，在 C 下由客户端产生，**与 ADR 设想的「后端产出错误码」不同**。 | [来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:29] |

**结论**：C 方案的自述「保住 ADR 第 3/5 条」**部分成立**（文字上），但它**没有交代第 1/2/4 条怎么办**，而第 4 条「按用户分级限流 + 审计」是 ADR 里唯一带具体数字与依据的一条，直接引用学校限制[来源: @NEW/docs/adr/0001-服务端代请求边界由新后端重写.md:28]。C 方案的存在理由（避开限流）恰好与 ADR 的手段（限流 + 审计）**方向相反**：ADR 想在后端做限流，C 想把请求挪出后端。二者要么是 C 需要修订 ADR，要么是 C 需要被修订。

**严重度：重要**（不是技术错误，而是**决策层冲突**：C 实际上是对 ADR-0001 第 4 条的静默推翻）。

## 哪些是真问题，哪些是我多疑

这一节我按「我自己有没有把握」重新划一遍，避免把弱项混进强项里。

### 我认为是真的、且证据硬的（3 条）

1. **「许可」无法被学校验证，是装饰性的**（问题 1）。证据链完整：网关只认 cookie 里的票 + CAS ticket XML 校验，仓内未找到任何第三方 token 授权入口。这条几乎没有解释空间。
2. **票不出后端 ⇒ 客户端不能被识别为已登录**（问题 2 前半）。旧仓的直连能力完全建立在「票在客户端 + `withCredentials`」之上，这是代码级事实。
3. **ADR 第 4 条在 C 方案下无处落地，且 C 方案的文字里没有承认这一点**（问题 6）。这是文档级事实，可逐条指到 ADR 行号。ADR 会不会因为 C 被修订是维护者的决定，但「C 没有交代」是事实。

### 我认为是真的、但属于「结构性风险」而非「已证实错误」（2 条）

4. **客户端对「票死」的判定依赖跟随重定向后的最终 URL**（问题 2 后半）。这条我是从 `request.ts:206` 的 `responseURL` 用法 + 编码器只对真站改写推出来的。**我要明确标注这是推论，不是一手结论**：仓内没有任何一处说「票死时客户端会拿到什么」。**仓内未找到**该行为的一手记录。它的分量在于：C 方案的闭环依赖这一环，而这一环恰好是未验证的。
5. **15 秒限制的作用维度未知**（问题 3）。这条我**无法判定**，只能指出「C 方案的立论依赖一个仓内没有的假设」。若维护者手上有「按账号」的实测或须知原文，这条立刻降级为「次要多疑」；目前它只能是「重要的未知」。

### 我认为**是我多疑**的（2 条，主动撤回）

6. **「许可会被中介/代理重放」**——我一度想写这条，撤回。理由：仓内**未找到**任何中间人捕获的场景记录；把凭据逐请求下发给客户端本就是把信任边界画在客户端，这一点在方案 A 里同样存在，不是 C 独有。**这条不成立，不写进结论。**
7. **「客户端自签许可 = 客户端可伪造访问」**——也撤回。因为许可**根本不被学校校验**（问题 1），所以伪造它没有任何收益，客户端想请求什么本来就由它自己的票决定。**这条不成立**。这也反过来加强问题 1：一个「谁能伪造都无所谓」的东西，要么证伪它的必要性，要么它其实不是许可，而是别的东西（比如审计用的流水号）——那就该按流水号来叫、按流水号来设计。

### 关于「是不是我在小题大做」

有一条值得自我校准：C 方案**没有**引入 SSRF（因为后端不再代请求），也**没有**把票写进日志/MMKV（旧规格明确禁止把票写 MMKV[来源: @OLD/docs/nongyu-rn-app/specs/WebVPN传输适配.md:21]，而旧实现恰恰违反了这一点——`SecureStore.setItemAsync(TICKET_KEY, value)`[来源: @OLD/apps/nongyu-rn-app/src/modules/jiaowu/auth/webvpnTicket.ts:31]）。这些不是 C 的问题。**C 的问题集中在「它承诺的分离（执行 vs 票据）在协议层面做不到」**，而不是它引入了新的安全隐患。

## 如果方案不成立，最小修改是什么

先声明：以下只列**能让 C 方案文字自洽的最小改动**，不替维护者重新拍板方案选型（那是维护者的事，也是这次红队不该越界的地方）。

### 路径一：承认票在客户端（把 C 改名为「A + 客户端直连」）

- 删掉「访问许可」整层。它是零功能的（问题 1、5）。若需要审计，改用**后端签发的流水号 + 请求回执上报**，并明确它是**事后审计**而非**事前授权**，不要命名为「许可」。
- 把「票据不出后端」改为「**票据不落库、不入日志，只在中转后清除**」。C 与 A 的真实差异因此缩小为「票是否被后端短暂持有」——若这个差异对维护者不重要，C 相对 A 就没有独立价值。
- 客户端必然要有票；旧仓已有完整实现可重写（`NongyuWebVpnCookieModule.kt`、`webvpnTicket.ts`）。

### 路径二：票留在后端（把 C 收敛为「后端代理 + 前端限流」）

- 放弃「客户端直连」，C 的高频只读仍走后端，只在**客户端侧**加节流（例如同一用户的只读请求串行化 + 最小间隔）。
- 这一路径的好处是 ADR-0001 五条**全部自然成立**（限流、审计、错误码全在后端），不需要修订 ADR。
- 坏处是它正是 C 想要避开的「后端承压」——但按问题 3，「避开承压」本身的收益是**未经验证**的，不值得为它推翻 ADR 第 4 条。

### 无论走哪条路，都必须先补的三件小事（否则方案无法验收）

1. **把「15 秒限制按账号还是按 IP」查清**。这是 C 方案立论的第一根支柱，而现在仓内只有一句须知摘录[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN探索.md:327]。
2. **撤掉客户端重试或给它加门**：旧实现「网络错误最多重试 3 次、每次 1 秒」[来源: @OLD/docs/nongyu-rn-app/tech/WebVPN可重写契约清单.md:221]，与 15 秒间隔直接冲突；新方案若沿用会自打耳光。
3. **处理 ADR-0001 第 4 条**：要么修订 ADR（写明「高频只读不经后端，故分级限流只覆盖换票与写操作」），要么删掉 C。**不能让 C 实施而 ADR 不动**，否则文档先自相矛盾。
