## 一句话形状

> **`internal/school/secondclass/` = 一张配方表 + 一个记录子域。没有出站客户端、没有凭据存储、没有代理。**

这是本 effort 与 `school/jiaowu` 最根本的差别：jiaowu 有换票、建会话、代取页面；二课**什么都不碰**，只把「怎么请求」和「谁问过什么」管起来。

## 一、顶层域形状

### 决定：放进 `internal/school/` 下，不新建顶层域

```
internal/
├── school/                    ← 已有，学校相关能力的父包
│   ├── secondclass/           ← ★ 本 effort 新增
│   │   ├── doc.go
│   │   ├── recipe.go          # 配方表（61 个接口的静态定义）
│   │   ├── datatype.go        # 数据副本的受控 dataType 词表 + TTL
│   │   ├── handler.go         # 配方下发端点
│   │   ├── record.go          # 记录子域（审计 + 副本）
│   │   ├── recordhandler.go   # 记录读写端点
│   │   ├── schemavalidate.go  # go:embed JSON Schema 校验
│   │   ├── schema/            # *.json
│   │   └── targets.go         # 逻辑目标名常量
│   ├── jiaowu/                ← 已有，不改
│   ├── schoolauth/            ← 已有，不改
│   └── targets.go             ← 已有白名单
├── content/                   ← 已有，不改
├── message/                   ← 已有，E 组复用，不改
├── identity/                  ← 已有，D 组画像复用，不改
└── app/                       ← 装配层，新增接线
```

**为什么放 `school/secondclass/` 而不是顶层 `internal/secondclass/`**：

| 理由 | 说明 |
| --- | --- |
| 语义归属 | 二课与教务同属「学校提供的第三方系统」，`school/` 正是这层的容器 |
| 已有先例 | `school/jiaowu` 与 `school/schoolauth` 已经在里面，新增同族不破坏结构 |
| 共享白名单 | `school/targets.go` 的目标名白名单天然是二课要扩展的地方（ADR-0001 第 1 条） |
| 反例 | 若放顶层，`school/targets.go` 的白名单要跨父包引用，反而更绕 |

**与其它域的关系（全部单向，无互相 import）**：

```
identity ──(UserRepo/ProfileRepo)──┐
content  ──(不引用)                │
message  ──(不引用，E 组直接复用其表)├──> app 装配层 ──> secondclass
school/jiaowu ──(不引用)            │
school/schoolauth ──(不引用)        ┘
```

**关键：secondclass 不 import 上述任何域**。若需用户画像展示，通过 `platform.UserRepo` 读（identity 已实现的接口），而不是 import `internal/identity`。

## 二、platform 接口增量

### 决定：**零新增接口**

逐个核过现有 14 个 platform 接口，二课需要的全都有：

| 二课要什么 | 用哪个现有接口 | 为什么不新增 |
| --- | --- | --- |
| 配方表（静态数据） | **不需要接口**，`recipe.go` 里的 Go map 常量即可 | 配方是编译期静态数据，不是外部能力 |
| 记录数据副本 | `CacheStore`（jiaowu 已声明的四方法子集） | 副本就是「按 key 存 JSON + TTL」，与 jiaowu 缓存子域同形状 |
| 审计流水 | `AuditStore`（`Append`） | 已有，六字段够用（#63 定了不加字段） |
| 时间 | `Clock` | 已有 |
| 用户身份 | **不需要** —— `userID` 从 `CtxUserID` 拿，不查库 | 鉴权中间件已写入上下文 |
| 出站 HTTP | **完全不用** `HTTPDoer` | **后端零出站**是 #69 的核心，用了就是违规 |

**⚠️ `CacheStore` 的处置**：ityaowu 在 `internal/school/jiaowu/cache.go:38-43` 定义了 `CacheStore` 接口（四方法）。二课要用同形状，有两种做法：

- **A（推荐）**：把 `CacheStore` 提到 `internal/platform/cache.go`，jiaowu 与 secondclass 都依赖它。理由：它已经是「两个域都要用的形状」，留在 jiaowu 内部会让 secondclass 必须 import jiaowu（违反 README 第 1 条「业务域不互相 import」）。
- **B**：secondclass 自己再声明一份同形状的 `CacheStore`。缺点：同一接口两份声明，将来改一处忘另一处。

**选 A**。这是一次**接口上移**，不是新增能力——`platform.CacheStore` 的方法集与 `jiaowu.CacheStore` 完全一致，jiaowu 改为别名引用即可（`type CacheStore = platform.CacheStore`）。

**新增依赖的双确认（根 AGENTS.md）**：本决定**不引入任何新第三方依赖**——`jsonschema/v6` 已在 go.mod（#42 引入），缓存/审计/时钟全是现成的。故**无删除义务产生**。

## 三、中间件链与路由

### 路由（三 + 一，全部需会话 + NY1 签名）

> **2026-11-17 修订（维护者选 B）**：原方案是四条并列端点（recipe 与 record 各自独立）。
> 维护者指出「二课以读为主（61 里 47 读 / 14 写，学生视角 47:10）」，与教务的 cache 形态同构更省往返。
> **改为：读类走 cache 形态（配方塞在 `cache_miss` 里），仅写类保留独立 recipe 端点。**

```
GET    /school/secondclass/cache/:dataType        ← 读副本；命中直返 / 未命中回 cache_miss + 配方
POST   /school/secondclass/cache/:dataType        ← 客户端自愿回传（尽力而为）
DELETE /school/secondclass/cache/:dataType        ← 副本失效（60 秒节流）
GET    /school/secondclass/recipe/:recipeId       ← 仅写类用（写不经 GET，没有 miss 时机）
```

**为什么前三条与教务同构、第四条才独立**：读类请求本来就要先 GET，未命中时正好可以捎带配方——客户端一次往返就拿到。写类（报名/签到）不经过 GET，没有「未命中」这个时机，所以必须单独给一条 recipe 入口。

**为什么缓存前缀也带 `cache/`**：与教务 `/school/jiaowu/cache/:dataType` 形成对称——两个学校侧系统的缓存端点形状完全一致，客户端可以复用同一套处理逻辑。

**⚠️ 与教务的语义差异（必须写进 Spec 第 7 节）**：教务是「前端解析 HTML → **必须**回传 JSON」，不回传则下一个人拿不到；二课客户端拿到 JSON 就能直接用，回传纯属分享，**可能一直为空**。形态同构但约束强度不同，不得混为一谈。


### 中间件

**不加任何新中间件，不改链序**：

```
RequestID → NY1(适用时) → 鉴权 → [AdminOnly 仅 /admin] → 限流
```

三加一个端点**都不进 `publicPaths`、都不进 `publicReadablePaths`**（#63 §三），`IsPublicPath` 一行不改。**NY1 不豁免**（#63 §五）。

## 四、装配与状态

### 装配层接线（`internal/app/app.go`）

```go
// 二课域：无出站、无凭据，只需要缓存与审计
if cache != nil {                              // Redis 未配时不挂（沿用 #30 口径）
    scSvc := secondclass.New(secondclass.Options{
        Cache:  cache,                          // platform.CacheStore
        Audit:  auditStore,                     // platform.AuditStore（可为 nil）
        Clock:  clock,
        Logger: logger,
    })
    secondclass.Register(engine, scSvc)          // 三加一个端点一起挂
}
```

**降级策略（沿用 #30 缓存子域装配口径）**：

| 依赖缺失 | 行为 |
| --- | --- |
| Redis 未配 | **配方下发仍可用**（它是纯静态数据 + 审计），**记录端点不挂** |
| Redis 未配 | 记录端点访问返回 503 `cache_unavailable`（#63 表 A 已有此码） |
| AuditStore 为 nil | 审计静默跳过，不影响业务 |

**为什么配方端点不依赖 Redis**：配方是 `recipe.go` 里的静态 map，下发时只查内存 + 记审计。让它依赖 Redis 是无谓耦合。

### 状态

- **进程无状态**：副本在 Redis，审计在 PG，配方在编译期常量。
- **凭据不落进程内存**：`x-access-token` 由客户端持有，**后端从不接收**（#69）——所以装配里根本没有凭据相关的字段。

## 五、测试两层接缝

| 层 | 测什么 | 用真依赖？ |
| --- | --- | --- |
| **纯函数单测** | `recipe.go` 的配方表完整性（61 个 id 唯一、槽位合法）、`datatype.go` 的词表与 TTL 分组、schema 校验器的 Compile | 否 |

**客户端直连二课那段不进本仓测试接缝**——那段代码不在本仓（后端零出站），测不到也不该测。这是 #63 盲区声明在测试层的体现。
