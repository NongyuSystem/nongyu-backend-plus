# 应用发布 / 安卓安装包下载服务契约（Spec #80）

> 服务端实现：`internal/release/`，迁移 `migrations/0012_app_releases.sql`。
> 领域词定义见仓库根 `GLOSSARY.md` 的「应用与发布」段（**应用**、**应用发布**、**支持版本下限**）。
> 本文件只记录**两端之间的 HTTP 契约**与服务端落点，不重述决策理由。

## 1. 定位

客户端需要两件事：知道「服务器上的最新版本是哪一版」，以及把这一版的安装包拿到手。
本域只负责「存 + 下发 + 按版本码取最大」，不做投放、不做灰度、不做回滚。

**「同产品」在本域的规范表述是「同一应用」**：一个应用由 `applicationId`（Android 包名，
如 `com.nongyu.app`）唯一标识。「同产品安卓包」= 同一 `applicationId` 下的某个版本的包。

两层存储（与既有域共用同一套切换口径，不新增第二套配置）：

| 数据 | 落点 | 说明 |
| --- | --- | --- |
| 安装包字节 | 对象存储，key `releases/{applicationId}/{versionCode}/{随机id}.apk` | 配 `MINIO_ENDPOINT` 即 MinIO，否则回落内存实现（仅本地开发） |
| 元数据 | Postgres `app_releases` | 配 `DATABASE_URL` 即 PG，否则回落内存实现；包体**不进数据库** |

对象 key 每次上传唯一（含随机后缀）是刻意的：确定性 key 在「重复上传 → 登记失败 → 回滚删对象」
这条路径上，会把**线上已发布那版**的包体一起删掉（皮肤包域实测抓到的 bug），此处沿用同一教训。

## 2. 领域模型

一条**应用发布**由 `(applicationId, versionCode)` 唯一确定，字段：

| 字段 | 含义 |
| --- | --- |
| `applicationId` | 应用身份（Android 包名） |
| `versionCode` | 版本码，正整数。**「最新」判定的唯一尺度** |
| `versionName` | 版本名，人类可读（如 `1.4.2`），只作展示、不参与比较 |
| `minSdk` | 可选，安装包要求的最低 Android API；0 表示未填 |
| `minSupportedVersionCode` | **支持版本下限**：低于它客户端必须阻断使用 |
| `changelog` | 更新说明，可空 |
| `sha256` / `size` | 整包摘要与字节数 |

**「最新」= 该应用 `versionCode` 最大的那条记录。** 不使用激活指针，
因此也不存在「指针指向不存在版本」这类悬空状态。

## 3. HTTP 契约

成功响应是**裸业务结构体**，错误是 `{"code":"...","message":"..."}`（apperr 统一）。

### 3.1 App 侧（只读）

三个端点都要 **有效 App 会话** 且 **通过 NY1 请求签名**：

- 会话：本域路径**不在**公开可读清单内（`publicReadablePaths` 目前为空，业务一律要求认证）；
- 签名：本域路径**不在**签名豁免清单内（只有 `/healthz` 与 `/admin/*` 免签）。

`applicationId` 走 **query 参数**而非路径段：包名含点号，塞进 gin 的路径参数会与
「文件扩展名」类路由语义混淆，且路径里已有 `:versionCode` 这个数字段。

| method | path | 说明 |
| --- | --- | --- |
| GET | `/releases/android/latest?applicationId=…` | 最新版本元数据 |
| GET | `/releases/android/latest/pack?applicationId=…` | 最新版本包体 |
| GET | `/releases/android/:versionCode/pack?applicationId=…` | 指定版本包体 |

平台位 `/android/` 是刻意保留的：安装包与版本号在 Android（`versionCode` 整数）与
iOS（`CFBundleVersion` 字符串）上是两个不同的世界，共用一条路径迟早要分叉。
将来加 iOS 时新增 `/ios/` 段即可，既有路径不动。

`GET /releases/android/latest` 响应：

```json
{
  "hasRelease": true,
  "applicationId": "com.nongyu.app",
  "versionCode": 10402,
  "versionName": "1.4.2",
  "minSdk": 24,
  "minSupportedVersionCode": 10300,
  "changelog": "修了几个问题",
  "size": 48392011,
  "sha256": "<整包 sha256，小写 hex>",
  "downloadUrl": "/releases/android/10402/pack",
  "updatedAt": "2026-11-24T01:00:00Z"
}
```

**没有任何已发布版本时**返回 `200 {"hasRelease": false}`（不是 404）：
「尚无版本」是正常态（新应用第一次发布之前），404 会被很多 HTTP 客户端当成故障处理。

`downloadUrl` **只指向本服务**，绝不是对象存储地址或预签名 URL——后者会被外传成
可直接抓取的直链，绕过会话与签名。

`GET …/pack` 响应头：

| 头 | 值 |
| --- | --- |
| `Content-Type` | `application/vnd.android.package-archive` |
| `Content-Disposition` | `attachment` |
| `X-Nongyu-Apk-Sha256` | 整包 sha256（与上传时记录的一致） |
| `Content-Length` | 包字节数 |

body 为安装包字节，**流式转发**（服务端不把整包读进内存）。
客户端流程：查 `/latest` → 比对自身 `versionCode` → 若需升级则下载 →
校验 `Content-Length` 与 `X-Nongyu-Apk-Sha256` → 结论一致才交给安装器。

错误码：

| 状态 | code | 场景 |
| --- | --- | --- |
| 401 | `unauthorized` | 未登录 |
| 404 | `not_found` | 指定 `versionCode` 不存在；或 `/latest/pack` 时该应用尚无版本 |
| 400 | `validation_failed` | `applicationId` 缺失/非法；`versionCode` 非数字 |
| 500 | — | 对象存储不可用等基础设施故障 |

### 3.2 管理端（B 端上传登记）

挂在 `/admin/*`：`admin 会话（ScopeAdmin） + AdminOnly(role>=1)`，
NY1 签名豁免（浏览器拿不到 APK 密钥）。上传放这里而非 App 侧，是因为 NY1 中间件
会把整个 body 读进内存且上限仅 1 MiB，而安装包可达数百 MB。

| method | path | 说明 |
| --- | --- | --- |
| POST | `/admin/releases` | 上传登记（multipart/form-data） |

字段：

- `applicationId`（必填）：形如 `com.example.app`（字母开头的点分段，只含字母数字与下划线）；
- `versionCode`（必填）：正整数；
- `versionName`（必填）：非空；
- `minSupportedVersionCode`（可选）：非负，且**不得高于本次 `versionCode`**
  （否则是「发布即被自身下限阻断」的自相矛盾记录）；
- `minSdk`（可选）：整数；
- `changelog`（可选）；
- `file`（必填）：安装包本体，单文件上限 **300 MiB**（服务端用 `MaxBytesReader` 硬限）。

成功 `201` 返回登记后的版本条目（不含对象 key 等内部字段）。
失败：非法字段 `400 validation_failed`、重复版本 `409 conflict`、超体积 `413 payload_too_large`。

**版本不可变**：同一 `(applicationId, versionCode)` 只能登记一次，重复上传返回
`409 conflict`，且**在写对象存储之前就拒绝**（不写对象、不碰既有包体）。
理由是「同一版本号必须永远对应同一套字节」：否则装过旧包的设备与新装设备
会被认为是同一个版本却是两套字节——而安装包会被执行，这比皮肤包更严重。

上传顺序：① 格式校验 → ② 查重（已存在直接 409）→ ③ 写对象存储（唯一 key）→
④ 写元数据（唯一约束兜并发竞态）。任一失败都不留下「可被读到」的半成品。

## 4. 已知边界（不假装没有）

- **服务端不解析、不校验安装包。** `applicationId`、`versionCode`、`versionName`
  全部由管理端填写，服务端只做格式检查——不读包内 `AndroidManifest`、不核对包名、
  不验签名、不验 `minSdk` 是否与包内一致。因此**服务端无从证伪**填写的值是否与
  包内真实值相符，手误不会被发现。
- **误传一个更大的 `versionCode` 会永久成为「最新」，且本域没有撤回 / 下架 / 回滚手段。**
  原因是两条决策的必然结果：「最新」取最大值 + 不引入激活指针。若要补救，最小形状是
  加一条「撤回」（把某条置为不可下载），而不是引入整套回滚。
- **下载要求会话，因此未登录设备无法升级。** 这是维护者的明确选择（基本所有业务都要
  认证），不是遗漏。若将来要放开，须**先改鉴权口径**（把路径加入公开可读清单）再改本域。
- `X-Nongyu-Apk-Sha256` 不是「校验包」：它只回答「你下到的字节与服务器存的是不是同一份」，
  不证明这个包是官方构建、也没有对包内容做任何判定。

## 7. 待实测 / 边界

- 真实 MinIO 的 `Put`/`Get` 往返未在本域对真实 MinIO 跑过（内存实现已全绿）；
  接真实存储前应跑一次「上传 → 下载 → 比对 sha256」。
- PG 路径的 `0012_app_releases.sql` 由启动期 `Migrate` 幂等执行；接真实库前应在
  staging 跑一遍并确认唯一约束与 `(app_id, version_code DESC)` 索引生效。
- 300 MiB 上限是当前取值；若将来包体常态超过它，改契约常量即可（入口用同一个常量做硬限）。
