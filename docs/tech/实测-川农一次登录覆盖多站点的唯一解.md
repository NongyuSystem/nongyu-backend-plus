# 川农一次登录覆盖多站点的唯一解

> 状态：**已实测证实**（2026-11-10）。本文件不含任何凭据值。
> 知识库 ES 不可达，本条目暂存仓内，待恢复后补录。

## 结论：两张凭据，各管一半

```
凭据 1  go-admin-tgt（55 字符）  → 管「认证类站点」
凭据 2  ywtb Bearer（47 字符）   → 只管 ywtb 一个站
```

**不需要逐站登录。**

## 凭据 1：go-admin-tgt

### 获取
账密 + 验证码登录 `POST https://auth.sicau.edu.cn/api/v1/cas/login`，
响应 `Set-Cookie` 下发 `go-admin-tgt`（形如 `201690:TGT:xxx`）。

### 用法：对**任意已注册 appid** 换票

```
GET https://auth.sicau.edu.cn/api/v1/cas/login?appid=<站点UUID>
Cookie: go-admin-tgt=<tgt>
→ {"code":200,"msg":"登录成功","data":"<加密>","requestId":"<32hex>"}
→ DecryptYWTB(requestId, data) → {st, tgt, user, callbackUrl, users, uuid}
```

已知 appid（UUID）：

| 站点 | appid |
| --- | --- |
| 教务 jiaowu | `b54a2f27-f7ba-4b91-bbf0-3b2b12244d14` |
| 门户 / WebVPN | `aea49a21-6b26-4e8f-bcfc-80e3de591c93` |

拿到 `st` 后回投各站自己的 caslogin 端点建会话（教务即 `jiaowu.sicau.edu.cn/jiaoshi/aspsso/caslogin.asp?appid=..&ticket=<st>`）。

### 实测证据

| 测试 | 结果 |
| --- | --- |
| 教务 appid `b54a2f27` | `code=200`，解出 `st=ST:Mmk2Fqjr6KrV5uFeX1DM-…` |
| 门户 appid `aea49a21` | `code=200`，解出 `st=ST:lW-zilTbHD8-n-0j-QGYa…` |
| **随机 UUID** | **`code=500 未登录`** ← 说明 appid 必须已注册 |
| `/sso/login?appid=<名>` 带 tgt | 8 个站名全部返回 `cascallback=choose`（已识别登录态） |

### 注意区分：appid 有两种形态

- `/sso/login?appid=ywtb` —— `appid` 是**名字字符串**，用于前端 SSO 路由；
- `/api/v1/cas/login?appid=<UUID>` —— `appid` 必须是**已注册的 UUID**，用于后端换票。

用名字去打 `cas/login` 只有 `ywtb` 碰巧返回 200（因为它恰好被注册成那个名字），其余全部 500。

## 凭据 2：ywtb Bearer

### 为什么需要单独的
**ywtb 完全不认 `go-admin-tgt`**——带 tgt 打它的 API 一律 401。

### 获取
浏览器登录 ywtb 后，token 在 `localStorage` 的 `lifeData` 里：

```
lifeData.data.vuex_token  →  "<用户ID>|<随机串>"（约 47 字符；本文件不记录真实值）
```

前端拦截器逻辑（从其 index.js 提取）：
```js
if (custom.auth) header.Authorization = "Bearer " + vuex_token
```

### 用法

```
POST https://ywtb.sicau.edu.cn/api/m/v1/user/getUserInfo
Authorization: Bearer <token>
Content-Type: application/json
body: {}

→ {"code":200,"requestId":"<hex>","data":"<加密>"}
→ DecryptYWTB(requestId, data) → 完整身份
```

**路径坑**：axios 的 `baseUrl = "/api"`，所以代码里写的 `/m/v1/user/getUserInfo`
完整路径是 `/api/m/v1/user/getUserInfo`。直接打 `/api/m/user/getUserInfo` 会 404。

### 解密后的完整字段

```json
{"number":"<学号>","name":"<姓名>","gender":"男",
 "idcard":"<18位完整号>","phone":"<11位手机号>",
 "unit":"信息工程学院","birthday":"2007-01-14T08:00:00+08:00",
 "groups":["bzks"],"email":"","qq":"","status":1,
 "wechat":"...","expire_at":"2099-12-31T23:59:59+08:00",
 "avatar":"https://jiaowu.sicau.edu.cn/photo_zxs/2025/.jpg"}
```

**这是身份证号的唯一来源**（`idcard` 字段，完整号）。教务 `bjiben.asp` 没有身份证。

## 各站点技术栈与判定

| 站点 | 可达 | 技术栈 | 统一认证 |
| --- | --- | --- | --- |
| jiaowu 教务 | 302 | 传统 ASP（GBK） | CAS，appid `b54a2f27` |
| ywtb 一网通办 | 200 | uni-app SPA + Laravel | **自有 Bearer** |
| xsc 学工 | 200 | 传统 ASP/.NET | 待确认 appid |
| zjc 招就 | 200 | 传统 ASP，含 CAS 字样 | 待确认 appid |
| cwc 财务 | 200 | — | 待确认 appid |
| lib 图书馆 | 200 | 汇文 LibSicau | 含 CAS 字样，待确认 appid |
| webvpn | 302 | 自研 VPN 壳 | appid `aea49a21` |
| ecology 生态 | **000 不可达** | — | 需经 webvpn 访问 |

## 操作坑

1. **用外部 curl 打 ywtb 的 `/api` 接口会超时或返回 `000`**——改用浏览器内 `fetch`（同源、自带 cookie）才成功。
2. `POST /api/caslogin`（ywtb 自己的账密登录）连续三次超时，未采用；实际采用「浏览器取 token」。
3. 注入 `go-admin-tgt` 到浏览器 cookie 后，访问 `/sso/login?appid=<名>` 即自动完成 SSO 并生成 ywtb token。

# 补记（2026-11-10）：学工系统 xsgz 是唯一数据源

## 维护者决定

`https://xsgz.sicau.edu.cn` 的 detail 端点定为**唯一数据点**；
jiaowu 的 GBK 页面解析与 ywtb 的 getUserInfo 取数**全部 disable**。

理由：这个端点一次返回 **13 个分组**，几乎覆盖用户清单里所有字段，
包括教务与 ywtb 都给不了的身份证号、家庭住址、考生号、紧急联系人、
教育经历、家庭成员、经济情况。

## 端点与请求头（关键：三处极易写错）

```
GET https://xsgz.sicau.edu.cn/gateway/zovecenter-saip-xg-app-student/student/detail/<学号>
```

必须同时带这 5 个头 + 2 个 cookie：

| 名称 | 值 | 写错的后果 |
| --- | --- | --- |
| `h-zove-token` | main-app-access-token | 401 用户身份验证失败 |
| `h-zove-tenantid` | `XG` | 500 系统租户标识不能够为空 |
| `h-zove-source` | **`20000`** | 用主应用的 `20100` → 403 |
| `h-zove-appkey` | **`zovecenter-saip-xg-app-student`** | 用 `...-agg-pc` → 403 |
| `h-zove-userlevel` | **`XS`** | 漏掉 → 403 API 接口资源未授权 |
| `Cookie` | `go-admin-tgt` + `main-app-access-token` + `main-app-level-key` | 401 |

**最容易踩的坑**：主应用 `app.js` 里写的是
`H-Zove-Source: "20100"` / `H-Zove-AppKey: "zovecenter-saip-xg-agg-pc"`，
但**子应用** `subapp/student/static/js/app.*.js` 里是 `20000` /
`zovecenter-saip-xg-app-student`，且**多一个 `H-Zove-UserLevel`**。
照主应用抄会稳定 403「您访问的API接口资源未授权」。

## 三条取数路径的差异（为什么不能套用 jiaowu 的做法）

| 站点 | 取数机制 | 后端能否直接用 tgt 复现 |
| --- | --- | --- |
| jiaowu | `tgt → cas/login?appid=<UUID> → st → 回投建会话 → 抓 GBK 页面` | 能 |
| ywtb | 客户端交 Bearer，`POST /api/m/v1/user/getUserInfo` | 需客户端交 token |
| **xsgz** | 客户端交 `main-app-access-token`，带 5 个 `h-zove-*` 头调网关 | **需客户端交 token** |

xsgz 的 `cas/authCodeLogin?ticket=<st:userId>` 虽然存在，但
用 jiaowu 那种 appid 换出的 st 去调会 401——它要的是浏览器 SSO 重定向
产生、绑定自己 service 的 ticket。因此**沿用 ywtb 的模式：客户端交 token**。

## 落库设计（迁移 0004）

四张表，混合策略，既不丢字段也不怕上游加字段：

- `student_profiles` —— 用户清单里的常用字段建成正规列
- `student_profile_groups` —— 13 个分组的**完整原文**（jsonb），一字不丢
- `student_family_members` / `student_resumes` —— 两个列表分组独立成表

身份证号加密进 `id_card_sealed`（bytea），明文绝不落库；另存后四位便于展示。

## 实测验证链

1. 纯 curl 带齐 header → HTTP 200 / 7288 字节 / `code=0` ✓
2. Go `FetchXSGZStudentDetail` → 取到家庭地址、手机、紧急联系人 ✓
3. 迁移 0001~0004 真实执行 ✓
4. `ParseXSGZDetail` 解析 13 组 → 身份证后4=2614、年龄=19 ✓
5. `SaveXSGZProfile` 落 4 表 → 回读毕业学院/宿舍/家庭地址，子表 13 组/成员2/简历3 ✓

## 踩过的坑（都已修）

- **字段类型**：`personalInfoDto.height` 是 **number**（180），Go 里定义成
  `string` 会让整个响应 Unmarshal 失败。改用 `json.RawMessage` 或 `strField` 兼容。
- **占位符数不匹配**：`student_profiles` 49 列却写了 48 个 `$n` + 2 个 `now()`。
  手写大 INSERT 后必须数一遍：`列数 == 占位符数 + now() 数`。
- **取到数但没人落库**：`SaveXSGZProfile` 写好后长时间没有调用方。
  已用 `TestXSGZSource_TriggersOnDetail` 锁住。
- **迁移新增表会让守卫测试失败**：`platform` 与 `app` 两个包各自硬编码了
  表清单，加表要同步；手写测试 DDL 也要同步加表，否则列形状比对失败。

## 补充：8 个站点的真实性质

维护者最初预期「一次登录后 8 个站都能用」，逐站实测后：

| 站点 | 性质 | 有无个人数据 |
| --- | --- | --- |
| jiaowu 教务 | CAS 换票 | 有 |
| ywtb | 自有 Bearer | 有（身份证唯一来源，现已被 xsgz 覆盖） |
| **xsgz 学工** | SSO 网关 | **有（13 组，最全）** |
| xsc 学工部 | 资讯门户 | 无 |
| zjc 招就处 | 资讯门户 | 无 |
| cwc 财务 | 需额外授权，首页即「没有访问当前栏目的权限」 | 无 |
| lib 图书馆 | 资讯门户；其 opac 子系统是**独立账号体系** | opac 有但不认统一认证 |

# 附：xsgz token 获取与 detail 端点的环境识别（2026-11-10 实测）

这一节记录一次**走到尽头的探究**，目的是让后来者不要重复走弯路。

## 一、token 可以由后端换出来（正确接口）

之前很久一直用错接口，记录在此以免重犯：

```
❌ 错：POST /gateway/xg-agg-pc/cas/authCodeLogin?ticket=<ticket>     → 401
✅ 对：POST /gateway/xg-agg-pc/cas/login
        Content-Type: application/x-www-form-urlencoded
        body: ticket=<st>:<userId>
        header: h-zove-token / h-zove-source:20100 / h-zove-tenantid:XG
                / h-zove-appkey:zovecenter-saip-xg-agg-pc
```

`cas/login` 返回 `{code:"0", data:{token:"<608字符>", accountRespDtoList:[{account:"学号"}]}}`。

**完整链路（已验证可拿到有效 token）**：

```
后端持有 tgt
  → GET auth.sicau.edu.cn/api/v1/cas/login?appid=ywtb   （Cookie: go-admin-tgt）
  → 解密得 {st, users[0].id}
  → POST xsgz /gateway/xg-agg-pc/cas/login  form: ticket=st:userId
  → 得到 608 字符 token
```

这个 token **是有效的**：用它调 `POST /gateway/xg-agg-pc/user/checkUserAndGetUserLevel`
返回 `200 {"data":{"userLoginType":"STUDENT","loginLevels":[{"levelNo":"XS",...}]}}`。

## 二、但 detail 端点有客户端环境识别

用同一个 token（实测与浏览器在用的是**完全相同**的 `809924ea…`，608 字符）调：

```
GET /gateway/zovecenter-saip-xg-app-student/student/detail/<学号>
header: h-zove-token / source:20000 / tenantid:XG
        / appkey:zovecenter-saip-xg-app-student / userlevel:XS
```

| 客户端 | 结果 |
| --- | --- |
| 浏览器（同 token、同 5 个头、**credentials=omit 不带 cookie**） | **200 / 7109 字节** |
| curl（HTTP/1.1） | 500 验证权限异常 |
| Go（HTTP/1.1） | 500 |
| Go（强制 **HTTP/2.0**） | 500 |
| PowerShell / .NET | 500 |

四种独立 HTTP 客户端全部 500，只有浏览器 200。

### 已逐个排除的因素

- **协议版本**：强制 h2 仍 500。
- **cookie**：浏览器用 `credentials:"omit"` 仍 200 → detail **不需要任何 cookie**。
- **Origin 头**：`https://xsgz.sicau.edu.cn` / 空 / `null` 三种取值都 500。
- **token 来源**：curl 换出的 token 与浏览器当前使用的**是同一个值**，不是"不同 token"问题。
- **5 个 h-zove 头缺哪个**：在浏览器里逐个移除验证，全部必需且已全部带上。

### 结论

> **⚠️ 此结论已被推翻（同日后续实测）。** 真实原因不是客户端环境识别，
> 而是**我用错了 token**：cas/login 换出的 token 与浏览器实际持有的 token
> 前 256 位相同、后 352 位不同，只有后者的那个能取数。
> 用浏览器的真实 token 在 curl 里请求同样返回 **200 / 7288 字节**。
> 详见文末「结论更正」一节。

## 三、因此的架构结论

**`detail` 端点只能在浏览器环境里调通。** 所以：

- 后端可以做：换 token、调非 detail 的普通接口（`/user/info`、`checkUserAndGetUserLevel` 等）。
- 后端**做不到**：自己取 detail 的 13 组档案数据。

可行方案（当前采用）：**客户端在浏览器/WebView 里调 detail，把 JSON 整包交给后端存**。
后端不需要理解 13 个分组的内容，直接交给 `SaveXSGZProfile` 落库即可。

后期若要继续探究，从这里接着走：抓一次浏览器成功的 detail 请求做 TLS 指纹比对。

# 结论更正（2026-11-10 后续实测）

上一节「detail 端点有客户端环境识别」的结论**是错的**。真实原因是我用错了 token。

## 推翻它的实验

把**浏览器 cookie 里的真实 token**（608 字符）原样交给 curl：

```
GET /gateway/zovecenter-saip-xg-app-student/student/detail/202502204
h-zove-token: <浏览器真实 token>
h-zove-source: 20000 / h-zove-tenantid: XG
h-zove-appkey: zovecenter-saip-xg-app-student / h-zove-userlevel: XS
```

→ **HTTP 200，7288 字节，完整 13 组数据**。

**所以不存在客户端环境识别，也不需要 uTLS、不需要 h2、不需要任何 cookie。**
TLS 指纹那条路（已实测 uTLS + http2 仍 500）是白费功夫，根源是 token 不对。

## 真正的差异：token 有两个不同的值

| 来源 | 前 256 位 | 后 352 位 | 能取 detail 吗 |
| --- | --- | --- | --- |
| 浏览器 cookie 中的 | 相同 | **A** | ✅ 200 |
| 后端 `cas/login` 换出的 | 相同 | **B**（每次还不同） | ❌ 500 |

实测 `cas/login` 连续换两次，得到的 token **前 256 位相同、后 352 位不同**，
说明后段是每次生成的会话标识；但**这两次换出来的都取不到 detail**。

结论：**`cas/login` 返回的 token ≠ 能用于取数的 token。**
浏览器最终持有的 token 还有一步变换，这一步尚未找到。

## 顺带纠正的其他错误

1. **`check-necessary` 在 curl 里返回 400 NPE** 不是权限问题，是缺 `H-Zove-ClientType` 头。
   加了这个头之后 `cas/login` 才会返回 200（否则报「客户端类型不能够为空」）。
2. **`H-Zove-ClientType: PC` 是 `cas/login` 的必需头**，之前漏了导致偶发失败。
3. 五个 `h-zove-*` 头仍然全部必需（逐个移除验证过），但**不需要任何 cookie**。

## 当前状态与下一步

- ✅ 明确知道「什么样的 token 能取数」（浏览器 cookie 里的那个）。
- ❌ 还不知道「这个 token 怎么由后端生成」。

下一步要查的：浏览器 `redirect.js` 里 `Object(s["i"])(e.data.token)` 这个 `s["i"]`
（setToken），以及它在此之前是否还调了别的接口做二次加工——
`cas/login` 返回的 token 到 cookie 之间应该还有一步。

# 二次更正：token 结构与签名段（2026-11-10 继续实测）

## 已确证：后端完全能取数，不存在环境识别

用浏览器 cookie 里的真实 token，**纯 curl**（无 cookie、无浏览器、无 TLS 伪装）：

```
GET /gateway/zovecenter-saip-xg-app-student/student/detail/202502204
h-zove-token: <真实 token>
h-zove-source: 20000 / h-zove-tenantid: XG
h-zove-appkey: zovecenter-saip-xg-app-student / h-zove-userlevel: XS
→ HTTP 200，7288 字节，完整 13 组
```

**uTLS、HTTP/2、cookie、Origin 全都是无用功。** 唯一的变量就是 token 本身。

## token 的真实结构

608 位**纯 hex**（= 304 字节），四段：

| 位置 | 长度 | 性质 |
| --- | --- | --- |
| 0–255 | 256 | **身份段**：所有 token 完全相同 |
| 256–351 | 96 | **会话段**：每次不同 |
| 352–479 | 128 | **固定段**：所有 token 完全相同（疑似密钥标识） |
| 480–607 | 128 | **签名段**：每次不同 |

## 关键对照（同一浏览器内做的）

| 接口 | `login2` 换的 token | cookie 里的 token |
| --- | --- | --- |
| `/user/info` | 200 | 200 |
| `checkUserAndGetUserLevel` | 200 | 200 |
| **`student/detail`** | **500** | **200** |

**两个 token 对普通接口表现完全一致，只有 detail 不同。**

所以 detail 端点要求的不是「有效 token」，而是**带特定签名的 token**。
`cas/login` 和 `user/login2` 换出来的签名段都不对，只有浏览器 SSO 流程最终写进
cookie 的那个才对。

## 试过但失败的路径（都不要再试）

| 尝试 | 结果 |
| --- | --- |
| `cas/authCodeLogin?ticket=` | 401 |
| `cas/login` + form `ticket=st:uid` | 200 但 token 取不到 detail |
| `user/login2` + `{unionId, account, accessSource:30100}` | 200 但 token 取不到 detail |
| `user/enterHall` | 200，但响应体和响应头里都没有 token |
| uTLS 伪装 Chrome TLS 指纹 + HTTP/2 | 仍 500（因为 token 不对） |

## 下一步该查的（留给后来者）

签名段是「服务端用私钥签、客户端只持有」的形式，正常无法伪造。
所以要找的是：**浏览器 SSO 回跳后，第一个 Set-Cookie 写入 token 的那个响应是哪个**。
做法：清空 cookie → 走一次完整 SSO → 用 DevTools 的 Network 面板按时间顺序看
第一个带 `Set-Cookie: main-app-access-token` 的请求。

`redirect.js` 里 `U(s["i"])(e.data.token)` 的 `s["i"]` 是模块 5581 的 setToken，
其中可能还有一次变换（如与 accessSource 或 deviceId 拼接后再签名）。

# 最终结论：后端完全可行（2026-11-10 定论）

前面几节的「环境识别」「签名段不可伪造」等结论**全部作废**。
真实原因只有一条：**我漏了 `enterHall` 这一步**。

## 后端自给自足的完整链路（已用项目正式 API 跑通）

```
后端只持有 go-admin-tgt
  ↓
① GET  auth.sicau.edu.cn/api/v1/cas/login?appid=ywtb
   Cookie: go-admin-tgt=<tgt>
   → 解密得 {st, users[0].id}
  ↓
② POST xsgz /gateway/xg-agg-pc/cas/login
   Content-Type: application/x-www-form-urlencoded
   必需头: H-Zove-Source:20100 / H-Zove-ClientType:PC
          / H-Zove-TenantId:XG / H-Zove-AppKey:zovecenter-saip-xg-agg-pc
   body: ticket=<st>:<userId>
   → {code:"0", data:{token:"<608 字符>"}}
  ↓
③ POST /gateway/xg-agg-pc/user/checkUserAndGetUserLevel
   → {loginLevels:[{levelNo:"XS", units:[{unitType:2, unitNo:"419"}]}]}
  ↓
④ POST /gateway/xg-agg-pc/user/enterHall
   body: {"departNo":<unitNo>,"userStateLevel":<levelNo>,"userType":<unitType>,"accessSource":"30100"}
   → 建立 detail 所需的权限上下文  ★★★ 就是这一步
  ↓
⑤ GET  /gateway/zovecenter-saip-xg-app-student/student/detail/<学号>
   必需头: H-Zove-Source:20000（子应用）/ H-Zove-AppKey:...-app-student
          / H-Zove-TenantId:XG / H-Zove-UserLevel:XS / H-Zove-Token
   → 200，13 组档案，约 7.9KB
```

## 实测证据（同一个 token 的对照）

| 步骤 | 结果 |
| --- | --- |
| cas/login 拿到 token，**直接**打 detail | **500 验证权限异常** |
| 先 `checkUserAndGetUserLevel` 再 `enterHall`（同一个 token） | — |
| enterHall 之后**同一个 token** 再打 detail | **200 / 7875 字节** |

**同一个 token，只差 enterHall 这一步。** 之前所有「换 token 方式不对」「签名段不对」
的推断都是被这个 500 误导出来的。

## 已落地的代码

`internal/school/schoolauth/sso.go`：

- `FetchXSGZToken(ctx, doer, authBase, tgt)` —— 后端用 tgt 自取 token（步骤 ①②）
- `EnterXSGZHall(ctx, doer, baseURL, token)` —— 升级权限上下文（步骤 ③④）
- `FetchXSGZStudentDetail(...)` —— **内部自动调用 EnterXSGZHall**，
  调用方不必知道顺序（步骤 ⑤）
- `XSGZSource.FetchIdentity` —— token 来源优先级：客户端交的 → 后端用 tgt 换 → 配置注入
