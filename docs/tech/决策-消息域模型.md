## 决议（Q1~Q6 全 A）

**Q1 存储形态 = 单表 per-user 投递行**：一行 = 「一个收件人的一条消息」。字段：`recipient_id`、`kind`(通知/内部信)、`source_domain`+`source_object_id`（通知指来源；内部信为空）、`title`/`body`、`read_at`、`deleted_at`、`created_at`。per-user 已读、可删、未读计数**天然成立**，一个模型覆盖两类形态。
- **已记录的规模代价**：广播型公告 fan-out 行数**随收件人线性增长**（全校全员公告 = 数万行/条），本期接受；Spec 落一条 fog「若公告 fan-out 成为瓶颈，后续可加广播型 watermark 优化」。
- 否决：内容表+投递表双表（行数照样增长、多一次 join、两类内容空值语义各写一套）；点对点行 + 全员水位双模型（两套已读语义、未读数要拼，公告已读回执若不启用则收益近零）。

**Q2 内部信发送范围**：**任何已登录用户 → 任何已存在用户**，不限好友关系。约束：**不能发给自己**、收件人必须存在（**fail-closed**）、正文长度上限、按发送者**频率限制**（复用既有 `RateLimitMiddleware` 口径）、**实名不匿名**（与帖子域刻意相反，Spec 须写明）。防骚扰本期只做限频，不做拉黑/举报（留 fog）。

**Q3 合并/去重位进模型**：对 `kind=通知` 建 **`(recipient_id, kind, source_domain, source_object_id)` 部分唯一索引**（内部信因 source 为空不参与）；同键重复触发走 **upsert（累加计数 + 保持未读）**，不插新行。→ 为 [#48](https://github.com/NongyuSystem/nongyu-backend-plus/issues/48) 的「同一帖子短时间多点赞去噪合并」提供**物理承载**（本票给承载、#48 给规则）。需计数列。

**Q4 已读与未读数**：`read_at`（null = 未读）；支持 **单条已读**、**全部已读**（按当前过滤条件批量置 `read_at`）、**软删**（`deleted_at`，不计未读）；**多端合并天然成立**（同一行天然一致）；**未读数 = `count(read_at is null and deleted_at is null)`**，走 PG 索引 `(recipient_id, read_at)`，**不加 Redis 计数器**（避免双写漂移；缓存若确需留 #51）。

**Q5 端点契约**：`GET /messages`（**游标分页**、`created_at` 倒序、按 `kind` / 仅未读过滤）、`GET /messages/unread-count`、`PATCH /messages/:id/read`、`POST /messages/read-all`、`DELETE /messages/:id`（软删）、`POST /messages`（**仅 `kind=内部信`**，user→user；通知**不接受外部直接建**）。信封沿用 `{code:string, message}`；路由挂**本域自己的前缀**下（不塞进 `/posts` 或 `/announcements`）。

**Q6 保留期/清理 + 推送通道（票面要求「先给判断」）**：**保留期本期不拍具体天数** —— Spec 只留「超过 N 天且已读的软删消息可被清理」的运维口，**N 交 [#51](https://github.com/NongyuSystem/nongyu-backend-plus/issues/51) 定**；**推送通道本期只做站内拉取**（不做厂商推送/APNs/邮件），通道留 fog（GLOSSARY「通知」的 `_Avoid_` 已点名「推送（通道属后续 Spec）」）。

## 派生项（票评「下一轮才问」的 2 项，按「按推荐」保守收敛，可回滚）

- **D1 通知正文的渲染归属**：**触发方写入时落库快照**（`title`/`body` 由触发方渲染好写入），**不做读时按 source 实时渲染**。理由：来源被软删后消息仍可读、读路径无跨域 join、与单表模型一致。代价：来源改文案后旧通知不跟随（快照语义，Spec 写明）。
- **D2「发给自己过滤」的落点**：**模型层不 insert**（服务写入口统一拒绝 `recipient_id == actor_id`，fail-closed），而不是只在 #48 编排层过滤。理由：多一条写入来路就少一处漏；#48 仍应在编排层再判一次（双保险）。
- 「消息端点鉴权口径」与「未读数是否加缓存」**不在本票裁**：前者归 [#46](https://github.com/NongyuSystem/nongyu-backend-plus/issues/46)，后者归 #51。
