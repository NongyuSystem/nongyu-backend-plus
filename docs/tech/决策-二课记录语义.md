# 决策：二课后端「记录」的确切语义（审计流水 + 数据副本）

> **性质**：wayfinder map [#58](https://github.com/NongyuSystem/nongyu-backend-plus/issues/58) 子票 [决议：读类后端承载的端点契约与缓存语义](https://github.com/NongyuSystem/nongyu-backend-plus/issues/61) 的决议产物。
> **本票已改名**：原题「读类后端承载的端点契约与缓存语义」的前提已被 #69 推翻，实际决议对象是「**后端『记录』记什么**」。
> **不是实现方案、不产可运行代码**。
> **拍板**：2026-11-16，五题全 A（Q2 = 方案 ③「两者都做」）。

## 〇、题干为什么换了

原题第 1 优先问题是「读类请求是后端持凭据代取，还是下发地址让客户端直连后回传」。但 [#69](https://github.com/NongyuSystem/nongyu-backend-plus/issues/69) 已把终点改为「**读写都在客户端，后端只做两件事：发怎么请求 + 记录**」。

于是本票唯一还活着的问题是：**「记录」到底记什么**。配方形状归 [#62](https://github.com/NongyuSystem/nongyu-backend-plus/issues/62)（管「怎么发」），本票管「记什么」。

## 一、决定：两条记录线并存，语义不同、不可互替

### 线 A：审计流水（**必有**）

| 项 | 内容 |
| --- | --- |
| 记什么 | `requestID`、`userID`、`action`、`target`（逻辑目标名）、`result`（结果码）、`occurredAt` —— 沿用既有 `AuditEntry` 六字段，**不加字段** |
| 何时写 | 每次配方下发（`secondclass.recipe_issue`）与每次数据副本写入（`secondclass.record`） |
| 写失败 | **不阻断主流程**，满则丢弃计数（沿用 `AuditStore` 旁路语义，`internal/platform/mail.go:415-428`） |
| 绝不记 | PU token、GPS 坐标、扫码时间戳、二课响应体、二课业务数据内容（#63 §六 铁律） |

**为什么必有**：后端经手的交互必须留痕（ADR-0001 第 4 条），且这是客户端不上报数据时**唯一**能证明「谁问过什么」的东西。

### 线 B：数据副本（**尽力而为**）

| 项 | 内容 |
| --- | --- |
| 记什么 | 客户端取回的二课 JSON，**按 dataType 分类存** |
| 谁能写 | 只有**已认证本人**能写**自己**的副本（键含 userID，见 §三） |
| 写失败/不写 | 视为正常（客户端可以不上报），后端**不得**因此报错或降级 |
| 可信度 | **明确接受：客户端回传不可验证真伪**（可伪造、可不上报、可只报一部分）。后端只做**形状校验**，不做真伪校验 |

**为什么做**：维护者原话「**类似爬取二课活动的这种功能在后端**」是明确诉求。不做副本，后端永远没有二课数据，这句话就落不了地。

**为什么是「尽力而为」而不是「必有」**：后端零出站（#69），拿数据只能靠客户端自觉上报——**后端没有任何强制手段**。把它写成「必有」是自欺。

## 二、复用 jiaowu 缓存子域，不另建

**决定：数据副本复用 [jiaowu/cache.go](<internal/school/jiaowu/cache.go>) 的同一形状**，只换 dataType 词表与 schema。

### 复用什么（已是现成实现）

| 机制 | jiaowu 现状 | 二课沿用 |
| --- | --- | --- |
| `CacheStore` 接口 | 四方法：`Get` / `Set` / `Delete` / `TryAcquire`（`cache.go:38-43`）；只声明用到的方法，业务域不依赖 `*platform.RedisCache` 具体类型 | ✅ 同一接口 |
| **TTL 与 stale 拆两个语义** | Redis TTL = stale 上限 + 1 天缓冲；新鲜度窗口 = 每类 TTL（`cache.go:8-24` 有完整说明，含「为何不能合一个」） | ✅ 同一拆法 |
| schema 校验 | `go:embed schema/*.json` + 启动期一次 Compile、fail-fast（`schemavalidate.go:1-35`）；15 份 schema 在 `schema/` 下 | ✅ 同机制，二课自己一套 json |
| 回传体上限 | 1 MiB（`MaxBytesReader`） | ✅ 沿用 |
| 失效节流 | 60 秒（`refreshInterval`） | ✅ 沿用 |
| 受控 dataType 词表 | 15 个 + `ParseDataType` 白名单（`datatype.go:20-35`），未知名一律拒，**绝不把用户输入当键的一段** | ✅ 同结构，二课自己一套名字 |

### 必须按二课改的四处

1. **`parser` 字段不要**。jiaowu 的 recipe 有 `parser`（`jiaowu-course-v1` 等），因为客户端要按解析器名解析 HTML。二课是 JSON API，**没有这一步**。
2. **`session` 状态位不要**。jiaowu 有 `session: ok/unavailable`，因为「后端建会话可能失败但仍是 200」。二课后端**不建会话**（凭据在客户端），这个态不存在。
3. **海边界不同**：jiaowu 直连地址校外不可达（暴露面被网络边界收窄）；二课 `jk.sicau.edu.cn` **公网可达**——所以二课的「地址+凭据下发」风险面更大，鉴权与限流按 #63 口径执行，不因 jiaowu 先例放松。
4. **`shape` 三分法要重判**：jiaowu 的 15 类分「数组 8 / 单对象 3 / 包装对象 4」。二课的响应形状**必须按真实响应定**，不能照抄 jiaowu 的三分——因为二课有三套响应壳（`BaseResponse` / `RespVO` / `BaseRespVO`），`data` 的载荷形状与 jiaowu 不同。**这是 Spec 阶段的阻塞项**（见 §五）。

**为什么不另建**：jiaowu 那套是**同一形状的问题**（客户端回传 JSON、后端校验后缓存），且已踩过「TTL 与 stale 上限拆两个语义」的坑。另建一套会让同一个坑踩第二次。

## 三、数据副本的关键设计

### 3.1 dataType 词表（二课自己的，受控）

按 #59 的范围（A+B 61 接口），建议分组（**具体名字交 Spec 定，此处只定分组原则**）：

| 组 | 大致内容 | 变化频率 | 建议 TTL |
| --- | --- | --- | --- |
| `activity*` | 活动列表、活动详情、活动成员、活动状态 | **快**（名额、审核态会变） | **10~15 分钟** |
| `credit*` | 学期学分、申请类学分、导入明细、综测、排名 | 慢（学期级） | **6~12 小时** |
| `grade*` | 成绩单、成绩记录明细 | 慢（学期级） | **6~12 小时** |
| `goodfaith` | 诚信值 | 中（随报名/签到场次变） | **30~60 分钟** |
| `rule*` | 学分规则说明 | **极慢**（几乎不变） | **24 小时** |
| `actbase*` | 活动类型/等级/标签/部落等基础数据 | 慢 | **6~12 小时** |

**原则**：TTL 按**数据变化频率**分组，不按接口分组。jiaowu 的分组（10 分钟/30 分钟/1 小时）也是一个数量级的三档；二课因活动名额变化更快、成绩更慢，**档位跨度更大**（10 分钟 ~ 24 小时）。

### 3.2 键维度

**键含 userID**（沿用 #32）：`nongyu:cache:<userID>:<dataType>`。

理由：二课数据是**本人视角**的（我的学分、我报名的活动），不同用户同一 dataType 内容不同。**不做共享键**——虽然活动列表理论上可共享，但「已报名的活动」这类字段是用户相关的，混存会串数据。若要优化公开数据的缓存效率，留到后续（与 #30 的同类结论一致：明确不作首版要求）。

### 3.3 写入路径

```
客户端取回二课 JSON
  → POST /school/secondclass/record/:dataType   （需农屿会话 + NY1 签名）
  → 1 MiB MaxBytesReader
  → dataType 白名单校验（未知一律拒）
  → JSON Schema 校验（不合格 → schema_rejected，一个字节都不写）
  → CacheStore.Set(key=userID:dataType, ttl=该类型的Redis保留期)
```

**不合格不写**（沿用 jiaowu）：坏数据永远顶不掉能读的旧数据。

### 3.4 读取路径

```
GET /school/secondclass/record/:dataType?fallback=1
  → 命中且 age ≤ 新鲜度窗口 → 返回，stale=false
  → 过期/未命中 → cache_miss 响应（附配方），客户端去取
  → 客户端取失败，带 fallback=1 再来 → age ≤ 7 天 → 返旧数据，stale=true
```

**stale 只由客户端上报失败触发**（沿用 #32），正常 GET 不会返回 `stale=true`。

### 3.5 7 天硬上限

沿用 jiaowu 的 `staleMaxAge = 7 天`（覆盖假期，但不把去年的活动当当前活动）。**Redis 实际保留 = 7 天 + 1 天缓冲**（抵抖动）。

## 四、为什么「审计必有、副本尽力」不能合成一条

三个理由：

1. **触发条件不同**：审计在**配方下发时**就记（必然发生）；副本要等客户端**真的取了并回传**才记（可能不发生）。
2. **可信度不同**：审计是后端亲眼所见（可靠）；副本是客户端自述（不可验证）。
3. **失败语义不同**：审计写失败不能影响业务（旁路丢弃）；副本写失败**本来就是常态**，不能当错误。

**若合成一条**，必然出现「要么把不可信的副本当审计用，要么把必然发生的审计降级为尽力而为」——两种都是错的。

## 五、留给 Spec 的阻塞项（必须解决才能施工）

1. **二课响应的 `data` 形状**：三套壳（`BaseResponse<T>` / `RespVO` / `BaseRespVO`）里，每类数据到底落在哪套、`data` 是什么形状（数组/对象/包装对象）——**离线样本只有请求参数、没有响应体**，必须在真账号 HITL 或 Spec 阶段用真实响应确认。**这决定 schema 怎么写。**
2. **`gid` / 学院名隐性依赖**（Q5=A 转 Spec）：活动详情是否含「主办部落名」「学院名」，取决于真实响应字段。若含，则 #59 的 61 接口范围可能要 +1~2；若不含，则明确不做。
3. **逐 dataType 的 schema 数量与命名**：建议按 §3.1 分组命名，但具体每个 dataType 一个 schema 还是按组一个，交 Spec 定。
4. **`schemaVersion` 是否存在**：jiaowu 的回传信封带 `schemaVersion`（#41），二课要不要也带？建议带——否则 schema 升级时无法拒收旧格式。
