# 服务端代请求边界由新后端重写

旧 RN 客户端规格 `docs/nongyu-rn-app/specs/WebVPN传输适配.md:20` 写的是「不做服务端代请求，不把 WebVPN 编成任意 URL 代理」，那条边界是**旧 App 的规格**。本仓 `README.md:3` 声明自己是独立于旧 monorepo 的全新仓库、不复用旧后端代码与部署链路，旧 spec 对新 Go 后端因此不具约束力。故本仓不沿用「有条件放宽」的说法，改为**为全新后端重写这条边界**：允许后端在明确的目标集合与约束条件下代请求，同时把「开放成任意 URL 代理」继续排除在外。拍板于 [放宽边界与 ADR：Q4「有条件放宽」的具体条件是什么](https://github.com/NongyuSystem/nongyu-backend-plus/issues/4)（Q1=a）。

## Status

accepted

## Considered Options

- **沿用「有条件放宽」**（map 初版口径）：把旧 spec 当成仍生效的规则，再列例外。否决理由：旧 spec 的标题与适用范围都是旧 RN 客户端（[WebVPN传输适配.md](<D:/IT/program/web-program/nongyu-system/docs/nongyu-rn-app/specs/WebVPN传输适配.md>) 第 1-5 行），而本仓明说不复用旧实现；给一个不适用于本仓的规则列例外，会让后来读代码的人以为存在一个正在生效的禁令。
- **整体废弃、不做替代**：既然旧 spec 不适用，就干脆不写边界。否决理由：`WebVPN探索.md:329` 记录的 SSRF 原理（持已认证网关会话即等价于访问任意校内 host）是**技术事实**而非旧仓规则，废弃文档不等于消除该风险。
- **为新后端重写边界（采纳）**：承认旧 spec 只管旧客户端，本仓重新规定允许的目标集合与硬约束。

## Consequences

- map 的 Q4 口径由「有条件放宽」改为「为新后端重写边界」；旧 spec 仅作历史对照引用。
- **本次重写只改文档规则，不改硬事实**：SSRF 原理、学校 ToS/风控、票据与网关会话的技术行为、真账号未验收项，全部继续生效，并作为具体条件的判据（[Go后端承载WebVPN的硬约束.md](<docs/tech/Go后端承载WebVPN的硬约束.md>)）。
- 具体条件（允许的目标集合、部署与鉴权、状态外置、审计与速率、302/Set-Cookie 处理）仍待本票第二轮确定；本 ADR 只锁定「由新后端重写」这件事本身。
- [GLOSSARY.md](<GLOSSARY.md>) 的「服务端代请求」词条随之确认：它是中性事实（后端代替客户端发起请求），不再与被废弃的禁令绑定。
