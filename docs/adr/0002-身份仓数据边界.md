# ADR-0002：身份仓（用户/登录/画像）的数据边界

- 状态：accepted（2026-11-08）
- 相关：[GLOSSARY.md](../../GLOSSARY.md)、[领域模型](<领域模型-用户与登录-消息.md>)、[ADR-0001](<0001-服务端代请求边界由新后端重写.md>)

## 背景

新建「用户与登录」能力时，有四处涉及敏感数据，需要一次性把边界钉死，避免后续每一张实施票各写一套：

1. **学校密码镜像**：维护者决定，学生用学校统一身份认证的账密登录成功后，把该用户在农屿的空密码写为学校密码。
2. **身份证号**：登录方式「学号 + 身份证后四位 + 姓名拼音首字母」需要校验身份证后四位。
3. **管理台权限**：沿用旧农屿的 role 三档（0 普通 / 1 管理员 / 2 超级管理员）。
4. **画像写入来源**：旧农屿在登录时用请求体整体覆盖画像字段，是已知安全洞。

## 决定

### 1. 学校密码**落库**（维护者拍板）

- 用户用学校账密登录农屿成功 → 将该用户的空密码写为学校密码；从未用账密登录过的用户，密码保持为空。
- 实现约束（不因「决定了存」而省略）：
  - AES-256-GCM 加密存储，密钥来自配置/密钥管理，不进代码仓、不进镜像。
  - 绝不出现在任何日志、审计、埋点、错误信息、接口响应中。
  - 仅在「向学校发起认证」时于内存中解密，用完即弃。
  - 提供「清除我的农屿密码」入口；清除后该用户只能走其它登录方式。

**已知且被接受的代价**：库泄即学校账号泄；学生改学校密码后农屿不自动跟随，需其用新密码再登录一次才更新。

### 2. 身份证号**只存后四位**（2026-11-09 修订，原决定作废）

**修订原因（实测事实）**：真实登录川农统一身份认证 `ywtb` 后，账户信息页显示
`证件号：650****2614` —— **完整身份证号被掩码，系统根本拿不到**。
原决定要求「加密存完整身份证号并允许接口返回」，但源头上没有这个数据，
继续按原决定写代码只会得到永远为空的字段。

**现决定**：

- **不存完整身份证号**；只存**后四位**（`id_card_suffix4`），来源是认证结果里掩码值的末四位。
- 原 `user_profiles.id_card_sealed`（密文字段）**不再写入**；迁移保留该列以便将来真能拿到完整号时不改表，
  但代码路径不写入、接口不返回。
- 登录方式「学号 + 身份证后四位 + 姓名拼音首字母」只依赖后四位，因此功能不受影响。
- **身份证号不使用加密密钥**，于是「两把独立密钥」简化为「密码镜像一把」。

**安全性反而更好**：敏感数据从「完整身份证号 + 可经接口返回」降为「4 位数字，不对外返回」，
泄露面显著缩小。

**对既有口径的影响**：知识库笔记《从川农教务 bjiben.asp 抓学籍》的隐私口径
「身份证号不落库」**重新成立**（本 ADR 先前的覆盖条款作废）。
该笔记的其余口径（个人电话、家庭电话不落库；家庭住址默认不对外返回）继续有效。

### 2b. 学院字段优先取认证结果里的「所属单位」

实测 `ywtb` 账户信息含 `所属单位：信息工程学院`，因此：

- **学院**取自认证结果的「所属单位」；
- **专业 / 班级 / 年级**仍需从教务 `bjiben.asp` 抓（认证不下发这三项）；
- 若认证结果没有「所属单位」，才回落教务抓取值。

注：知识库笔记称「统一身份认证不下发学院」——该结论对 `ywtb` 这个应用**不成立**，
但对其它入口（如某些 appid）可能仍成立，因此实现要按「有则用、无则回落」处理。

### 3. 管理台权限沿用 role 三档

- `0` 普通用户 / `1` 管理员 / `2` 超级管理员。
- 权限粒度是**整条路由**，不做资源级 ACL，不做权限点表（与旧农屿一致）。
- **role 以数据库为准**，令牌里的 role 只作提示、不参与判定（旧实现已有此约束，沿用）。
- 强制规则：
  - 判定兜底必须 **fail-closed**：任何「无法判定」的情形一律拒绝，不得默认放行。
  - 区分「查不到」与「基础设施故障」：前者按无权限处理，后者向上抛错，不得静默压成无权限（否则线上无从排查）。

### 4. 画像按字段分权

| 字段来源 | 谁能写 |
| --- | --- |
| 学校档案（姓名、学院、专业、班级、年级、**身份证号**、姓名拼音首字母） | **只允许服务端在学校认证/教务抓取成功后写入** |
| 农屿扩展（QQ、头像、偏好） | 只允许本人修改 |

客户端提交的画像字段**一律不得覆盖学校档案字段**。这条直接针对旧农屿的安全洞。

## 备选方案与否决理由

1. **不存学校密码，改为登录时转发验证**：体验一致、风险更低。维护者明确选择存，理由是要「默认账密可用」。否决。
2. **身份证号不落库，登录时实时比对**：符合既有隐私口径。但会要求每次走该登录方式都经学校认证取身份证号，且管理台无法展示。维护者选择落库并允许返回。否决。
3. **身份证只存后四位**：2026-11-08 曾因「管理台需要完整值」未采纳；
   2026-11-09 实测发现**完整号拿不到**，遂改为采纳。见第 2 节修订。
4. **存完整身份证号明文**：任何情况下都不可接受（个人敏感信息）。否决。

## 后果

正面：
- 四种登录方式与无感注册可以一次设计到位，不会因数据边界反复返工。
- 权限三档沿用旧口径，迁移时旧数据可直接映射。

负面（接受）：
- 本库成为**高敏感数据集中点**：学校密码 + 身份证号同时存在。必须配套加密、密钥管理、访问审计与最小暴露面。
- 身份证号可经接口返回，意味着**该接口的鉴权与审计等级必须是最高的**，任何越权读取都等同于批量泄露。
- 与知识库既有隐私口径出现分歧，已在第 2 节显式记录覆盖范围。
